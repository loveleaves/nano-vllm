## 执行摘要

模型适配（Model Adaptation）是指将一个已训练好的大语言模型（LLM）集成到特定推理框架或硬件平台上，使其能够正确、高效地运行的全套工程工作。其核心难点不在于单一技术，而在于多个层次同时对齐：**架构语义对齐、权重数值对齐、算子实现对齐、并行策略对齐、量化精度对齐**。

**5 条核心发现**：
1. 90% 的适配 bug 来自三类根因：权重 key 映射错误、位置编码参数不一致、注意力 mask 处理差异。
2. 精度验证必须分层做：先 logits 对齐（greedy），再采样一致性，最后 benchmark 回归。
3. 昇腾适配与 GPU 适配的最大差异在于算子替换层（CANN 算子 ≠ CUDA kernel），需逐层 dump 对比。
4. 量化适配不是精度损失问题，是精度损失**预算**问题——先确定可接受阈值再选方案。
5. 适配工作 60% 是调试，文档化每一个非显然的决策是降低后续维护成本的最高 ROI 动作。

### 2.5 建立可复现的 Golden Reference

Golden reference 是适配工作的**唯一真理来源**，一旦建立就不要改动：

```python
# golden_reference.py — 在 HuggingFace 环境中运行一次，保存结果
import torch, pickle
from transformers import AutoModelForCausalLM, AutoTokenizer

PROMPTS = [
    "你好，请用一句话介绍量子计算",
    "Explain gravity in one sentence.",
    "1 + 1 = ",
    # 覆盖：中文、英文、数学、代码……多样化
]

def save_golden(model_path, out_path="golden.pkl"):
    tok = AutoTokenizer.from_pretrained(model_path)
    m = AutoModelForCausalLM.from_pretrained(
        model_path, torch_dtype=torch.bfloat16, device_map="cuda"
    )
    m.eval()
    golden = {}
    for p in PROMPTS:
        ids = tok(p, return_tensors="pt").input_ids.cuda()
        with torch.no_grad():
            out = m(ids)
        golden[p] = {
            "logits_last": out.logits[0, -1].cpu().float(),   # 最后位置完整 logits
            "greedy_next": out.logits[0, -1].argmax().item(), # greedy 预测
        }
    pickle.dump(golden, open(out_path, "wb"))
    print(f"Saved golden to {out_path}")

save_golden("model_dir")
```

**比对时只看最后一个 token 的 logits**，原因：
- 整个序列所有 position 的 logits 保存体积太大
- 最后 position 最能体现 attention 和 FFN 的累积行为
- greedy next token 确定性高，适合做 pass/fail 判断

## 三、架构适配

### 3.1 注意力机制适配

注意力变体是适配最高频出错的地方，必须逐细节核对。

#### 3.1.1 MHA / GQA / MQA 区分

```python
# 从 config.json 读取关键参数
num_attention_heads      # Q heads 数量
num_key_value_heads      # KV heads 数量（GQA/MQA时 < num_attention_heads）
head_dim = hidden_size // num_attention_heads

# GQA 时的分组比
num_kv_groups = num_attention_heads // num_key_value_heads

# 关键：KV cache 维度是 num_key_value_heads 而非 num_attention_heads
kv_cache_shape = (num_blocks, block_size, num_key_value_heads, head_dim)
```

**常见错误**：误用 `num_attention_heads` 初始化 KV cache，导致显存分配异常或 OOM。

#### 3.1.2 MLA（Multi-Head Latent Attention）适配要点

DeepSeek V3/R1 使用 MLA，与标准 GQA 差异显著：

```
MLA 核心思想：
  - KV 通过低秩矩阵 C_KV 压缩（减少 KV cache 大小）
  - RoPE 解耦：Q 和 K 各有额外维度携带位置信息
  - 推理时可将 W_UK 和 W_UV 吸收进 W_Q/W_O，减少运算

适配要点：
1. KV cache 存储的是压缩后的 latent 向量 c_KV，而非展开后的 K/V
   shape: (num_blocks, block_size, kv_lora_rank + qk_rope_head_dim)
2. decoupled_rotary_pos_emb=True：RoPE 只加在额外的 rope 维度
3. absorb_kv_a_proj_with_mqa 优化：推理时可选择矩阵吸收以节省计算
4. 不要直接套 GQA 的 paged_attention kernel，需专用 MLA kernel
```

#### 3.1.3 滑动窗口注意力（SWA）

```python
# Mistral / Gemma3 使用局部+全局交替
sliding_window = config.sliding_window  # e.g., 4096

# 按层决定是否启用滑动窗口
# Gemma3: 每 6 层中 5 层用局部，1 层用全局
layer_is_sliding = (layer_idx % 6 != 5)

# KV cache 实现：滑动窗口层只保留最近 sliding_window 个 token
# 注意：PP 并行时需在 config.json 中声明 layer_types，
# 让各 stage 知道本 stage 哪些层用 sliding window
```

#### 3.2.2 RoPE 工程实现要点

```python
# 工程优化：预计算并缓存 cos/sin 表
class RotaryEmbedding(nn.Module):
    def __init__(self, dim, max_seq_len, theta):
        inv_freq = 1.0 / (theta ** (torch.arange(0, dim, 2) / dim))
        # 预计算 [max_seq_len, dim/2]
        t = torch.arange(max_seq_len)
        freqs = torch.outer(t, inv_freq)
        # 存为 buffer，避免每次 forward 重算
        self.register_buffer("cos_cached", freqs.cos())
        self.register_buffer("sin_cached", freqs.sin())

    def forward(self, q, k, positions):
        # 用 positions 索引，支持非连续位置（对 paged attention 关键）
        cos = self.cos_cached[positions]
        sin = self.sin_cached[positions]
        return apply_rotary_emb(q, cos, sin), apply_rotary_emb(k, cos, sin)

# 关键：positions 是实际 token 位置，不是序列内下标
# decode 阶段 positions 是 [context_len, context_len+1, ...]
```

#### 3.2.3 MLA 解耦 RoPE

```python
# MLA 中 RoPE 只作用于额外的 rope 维度
# q 的维度拆分：[q_head_dim] = [qk_nope_head_dim] + [qk_rope_head_dim]
# k 的维度拆分：[kv_lora_rank] + [qk_rope_head_dim]

q_nope, q_pe = q.split([qk_nope_head_dim, qk_rope_head_dim], dim=-1)
k_pe = k_pe  # 从 latent 向量单独投影得到

# 只对 pe 部分施加 RoPE
q_pe, k_pe = apply_rotary_emb(q_pe, k_pe, cos, sin)

# 拼回完整的 q/k 参与 attention 计算
q = torch.cat([q_nope, q_pe], dim=-1)
```

### 3.3 归一化层适配

```python
# RMSNorm（LLaMA/Qwen/DeepSeek 系列）
# 注意：没有 mean 减法，只有 RMS 缩放
class RMSNorm(nn.Module):
    def __init__(self, hidden_size, eps=1e-6):
        self.weight = nn.Parameter(torch.ones(hidden_size))
        self.variance_epsilon = eps

    def forward(self, x):
        variance = x.pow(2).mean(-1, keepdim=True)
        x = x * torch.rsqrt(variance + self.variance_epsilon)
        return self.weight * x

# 常见坑：
# 1. eps 值：不同模型不同，Qwen3 用 1e-6，需从 config.json 读
# 2. add_unit_offset：Gemma 系列 weight 初始化为 0，使用时要 +1
#    return (1 + self.weight) * x  # Gemma 的 RMSNorm
# 3. 前归一化 vs 后归一化：现代模型都是前归一化（pre-norm）
```

### 3.4 激活函数适配

```python
# SwiGLU（主流选择）
# gate_proj 和 up_proj 分开投影
def swiglu(gate, up):
    return F.silu(gate) * up

# GeGLU（Gemma 等）
def geglu(gate, up):
    return F.gelu(gate, approximate="tanh") * up

# 关键：FFN 的 intermediate_size 在 SwiGLU/GeGLU 中是 gate+up 共用尺寸
# 实际参数量 = 2 × intermediate_size × hidden_size（gate_proj + up_proj）
# config.json 中 intermediate_size 已是扩展后的值，不需要再乘 2
```

```python
        # 4. 汇聚专家输出（加权求和）

# - expert_parallel_size：EP 下每个 rank 只持有部分专家的权重
```

### 3.6 RoPE 扩展变体实现对比

现代模型普遍使用 RoPE scaling 扩展上下文长度，不同变体实现差异不小，用错会导致长文本精度严重下降。

#### 3.6.1 Linear（线性内插）

最简单，将位置除以 scale factor，压缩到预训练范围内：

```python
# positions 从 [0, max_len) 压缩到 [0, original_max_len)
scaled_positions = positions / scaling_factor
# 等效于 inv_freq 不变，只缩小位置索引
```

**适用**：快速 hack，精度不如 YaRN，适合 factor ≤ 4 的温和扩展。

#### 3.6.2 YaRN（Yet another RoPE extensioN）

针对不同频率维度分别处理，高频维度保持原始（不扩展），低频维度线性缩放，中间做平滑插值：

```python
# 关键参数（从 config.json 读取）
beta_fast = rope_scaling.get("beta_fast", 32)   # 高频边界
beta_slow = rope_scaling.get("beta_slow", 1)    # 低频边界
original_max = rope_scaling["original_max_position_embeddings"]

# 按 dim 决定缩放比例
def yarn_find_correction_range(low_rot, high_rot, dim, base, max_pos):
    low = max(math.floor(dim * math.log(max_pos / (low_rot * 2 * math.pi))
                         / (2 * math.log(base))), 0)
    high = min(math.ceil(dim * math.log(max_pos / (high_rot * 2 * math.pi))
                         / (2 * math.log(base))), dim - 1)
    return low, high
```

**适用**：Qwen2.5-72B-Instruct、Mistral-Large-2407 等主流长上下文模型，factor 可达 8–32。

#### 3.6.3 LLaMA3（频率混合插值）

将 inv_freq 按频率分三段：高频保持不变（短距离精度），低频线性缩放（长距离覆盖），中间平滑过渡：

```python
low_freq_factor  = rope_scaling["low_freq_factor"]   # e.g. 1.0
high_freq_factor = rope_scaling["high_freq_factor"]  # e.g. 4.0
old_max = rope_scaling["original_max_position_embeddings"]  # e.g. 8192

for i, freq in enumerate(inv_freq):
    wavelen = 2 * math.pi / freq
    if wavelen < old_max / high_freq_factor:
        pass                        # 高频：不改
    elif wavelen > old_max / low_freq_factor:
        new_inv_freq[i] = freq / factor  # 低频：直接缩放
    else:
        # 中间：平滑混合
        smooth = (old_max / wavelen - low_freq_factor) / (high_freq_factor - low_freq_factor)
        new_inv_freq[i] = (1 - smooth) * freq / factor + smooth * freq
```

**适用**：LLaMA-3.1/3.2/3.3，不能套 YaRN 实现，否则长文本精度会差。

#### 3.7.1 Gemma 系列：归一化权重偏置和 embedding 缩放

```python
# 这是训练时的设计，推理时必须保留

```

```python
# GLM-4 使用二维位置编码（block_position, position）
# 不能直接用标准 1D RoPE

# GLM 的 causal mask 比标准 decoder 多一个 prefix mask：
# prefix token 之间完全可见（双向 attention），
# generation token 对 prefix 可见、对后续 generation 不可见
# 适配时必须根据 input_ids 中的 [gMASK] sop 位置动态构建 mask
```

#### 3.7.4 DeepSeek MoE：norm_topk_prob 路由归一化

```python
# DeepSeek V2/V3 的路由归一化由 norm_topk_prob 控制
# norm_topk_prob=true  → 路由权重归一化后再加权求和（更稳定）
# norm_topk_prob=false → 不归一化，直接用 softmax 权重（原始 MoE）
```

### 4.4 健壮的 load_weights 实现

```python
def load_weights(self, weights: Iterable[Tuple[str, torch.Tensor]]):
    stacked_params = {
        "qkv_proj": ["q_proj", "k_proj", "v_proj"],
        "gate_up_proj": ["gate_proj", "up_proj"],
    }
    params_dict = dict(self.named_parameters())

    for name, loaded_weight in weights:
        # strip 模型前缀
        name = name.removeprefix("model.")

        # 处理 tie_word_embeddings
        if name == "lm_head.weight" and self.config.tie_word_embeddings:
            continue

        # 处理合并参数（qkv_proj / gate_up_proj）
        handled = False
        for merged_name, sub_names in stacked_params.items():
            for sub_idx, sub_name in enumerate(sub_names):
                if name.endswith(f".{sub_name}.weight"):
                    merged_key = name.replace(f".{sub_name}.weight",
                                              f".{merged_name}.weight")
                    if merged_key in params_dict:
                        # 按子权重顺序拼接到对应 slice
                        param = params_dict[merged_key]
                        chunk_size = param.shape[0] // len(sub_names)
                        param.data[sub_idx*chunk_size:(sub_idx+1)*chunk_size].copy_(
                            loaded_weight
                        )
                    handled = True
                    break
            if handled:
                break

        if not handled and name in params_dict:
            param = params_dict[name]
            assert loaded_weight.shape == param.shape, \
                f"Shape mismatch: {name} {loaded_weight.shape} vs {param.shape}"
            param.data.copy_(loaded_weight)
        elif not handled:
            logger.warning(f"Unexpected weight key: {name}")
```

### 4.7 权重加载的工程决策

**精度：什么时候用 FP32 加载？**

loading 阶段默认用 BF16/FP16（`torch_dtype=bfloat16`），节省内存、加快速度。以下情况才用 FP32 加载：
- 做精度对比 baseline（FP32 是数值上限，用来排查是否存在精度损失而非实现错误）
- 手动做量化 calibration（部分量化工具要求 FP32 输入）
- 执行权重统计分析（outlier detection 等）

**形状不匹配的第一反应：先判断是 TP 还是真错**

`load_weights` 里遇到 shape 不匹配，不要立刻报错——先确认是否因 TP 分片造成：
- `ColumnParallelLinear` 的 weight 在 output_dim（第 0 维）被切分，每个 rank 只有 `1/tp_size`
- `RowParallelLinear` 的 weight 在 input_dim（第 1 维）被切分
- `QKVParallelLinear` 的 Q/K/V 分别按各自的 heads 数切分

真正的形状错误通常是 key 映射到了错误的层（如 layer 0 的权重映射到了 layer 1）。

**GQA 权重的 repeat 问题**

部分早期 GQA 实现将 K/V 权重按 `num_kv_groups` 重复存储（每组 heads 都存一份），而主流推理框架（vLLM、MindIE）只存一份并在 attention 时动态 expand。加载时必须去重：
- 检查 `k_proj.weight.shape[0]` 是否等于 `num_attention_heads * head_dim`（重复存储）还是 `num_key_value_heads * head_dim`（正确）
- 若是重复存储，加载时只取 `[:num_key_value_heads * head_dim]` 的那一段

**tied embeddings 的三种处理方式及选择**

| 场景 | `tie_word_embeddings` | 处理方式 |
|------|----------------------|---------|
| LLaMA2 / Gemma | `true` | `load_weights` 中跳过 `lm_head`；forward 里 `lm_head.weight = embed_tokens.weight` |
| Qwen2/3 | `false` | 正常加载 `lm_head`，两者是独立权重 |
| 量化模型 | 通常分离 | 即使原始 tied，量化后 `lm_head` 通常保持 FP16 独立存储 |

```python
from vllm.model_executor.layers.linear import (
    ColumnParallelLinear, RowParallelLinear,
    QKVParallelLinear, MergedColumnParallelLinear,
)

    VocabParallelEmbedding, ParallelLMHead,
)
from vllm.model_executor.layers.rotary_embedding import get_rope

class YourModelAttention(nn.Module):
    def __init__(self, config, layer_idx, cache_config, quant_config, prefix=""):
        self.head_dim = config.hidden_size // config.num_attention_heads
        self.q_size = config.num_attention_heads * self.head_dim
        self.kv_size = config.num_key_value_heads * self.head_dim

        self.qkv_proj = QKVParallelLinear(
            hidden_size=config.hidden_size,
            head_size=self.head_dim,
            total_num_heads=config.num_attention_heads,
            total_num_kv_heads=config.num_key_value_heads,
            bias=getattr(config, "attention_bias", False),
            quant_config=quant_config,
            prefix=f"{prefix}.qkv_proj",  # prefix 必须传递！
        )
        self.o_proj = RowParallelLinear(
            input_size=config.num_attention_heads * self.head_dim,
            output_size=config.hidden_size,
            bias=False,
            quant_config=quant_config,
            prefix=f"{prefix}.o_proj",
        )
        # vLLM 统一 Attention 算子（自动选择后端）
        self.attn = Attention(
            num_heads=config.num_attention_heads,
            head_size=self.head_dim,
            scale=self.head_dim ** -0.5,
            num_kv_heads=config.num_key_value_heads,
            cache_config=cache_config,
            quant_config=quant_config,
            prefix=f"{prefix}.attn",  # 用于唯一标识 KV cache slot
        )
        self.rotary_emb = get_rope(
            self.head_dim,
            rotary_dim=self.head_dim,
            max_position=config.max_position_embeddings,
            base=config.rope_theta,
            rope_scaling=getattr(config, "rope_scaling", None),
        )

    def forward(self, positions, hidden_states, kv_cache, attn_metadata):
        qkv, _ = self.qkv_proj(hidden_states)
        q, k, v = qkv.split([self.q_size, self.kv_size, self.kv_size], dim=-1)
        q, k = self.rotary_emb(positions, q, k)
        attn_output = self.attn(q, k, v, kv_cache, attn_metadata)
        output, _ = self.o_proj(attn_output)
        return output
```

### 5.5 PP 层分配的工程经验

PP（流水线并行）是大模型多机部署的关键，但适配时坑比 TP 多，主要体现在**层分配不均导致的显存 OOM**和**特殊层归属问题**。

**层分配不均是 PP OOM 的首要原因**

vLLM 默认按层数均匀切分，但 embedding 层和 lm_head 的显存不计入"层数"统计。结果是第一个 stage（embedding + 若干 Transformer 层）和最后一个 stage（lm_head + 若干 Transformer 层）显存远高于中间 stage。

典型解法：给第一和最后一个 stage 少分配 1-2 个 Transformer 层，显式指定 `pp_rank_to_layers` 的分配方案（vLLM 支持 `--num_scheduler_steps` 和手动层分配 override）。

**含 MoE 的模型 PP 切分要格外小心**

MoE 层比 Dense 层显存大数倍（专家参数量），如果 MoE 层和 Dense 层混排（如 DeepSeek V3：每 3 个 Dense 层接 1 个 MoE 层），按层数均分会导致含 MoE 的 stage 显存爆炸。正确做法是按**参数量**而非层数分配。

**滑动窗口模型的 PP 声明**

Mistral / Gemma3 等混合滑动窗口的模型，PP 场景下每个 stage 必须能判断"本 stage 的哪些层是 sliding window 层"。这需要在模型配置或 vLLM 的 `LayerConfig` 中显式声明 `layer_types`，否则每个 stage 会按默认 full attention 处理，轻则精度异常，重则 KV cache 尺寸计算出错导致崩溃。

**PP 调试的隔离策略**

PP 出问题时，先改成 `pp=1, tp=N` 单 stage 验证精度，确认模型本身无误后，再逐步增加 pp stage 数来定位 PP 通信或层分配问题。永远不要在多故障变量的情况下调试。

### 5.6 vLLM 适配的快速验证路径

**不要在服务化环境下验证新模型**，使用 `LLM` 离线接口，从最小可复现用例开始：

1. **单 token prefill 验证**：输入短 prompt，`max_tokens=1`，对比 logits 与 golden reference——此步仅测 forward 正确性，排除采样和长生成的干扰
2. **greedy decode 短输出**：`temperature=0, max_tokens=20`，对比逐 token 输出——发现 KV cache 或位置编码的渐进错误
3. **批量不等长 padding 验证**：混入不同长度的 prompt，检查 attention mask 和 position_ids 的 padding 处理是否正确
4. **TP > 1 验证**：相同输入，`tp=1` vs `tp=2` 输出必须 bit-for-bit 一致；不一致说明某个 Linear 层的切分方向或 all-reduce 时机有问题

每一步验证通过再进入下一步，不要一次性把所有变量全部开启。

### 6.1.1 ATB 三层编程模型（官方架构）

ATB（Ascend Transformer Boost）采用三层结构，理解这三层是适配工作的基础：

```
┌─────────────────────────────────────────────────────────────┐
│  Model 层                                                    │
│  完整推理流程，Python 框架直接调用                            │
│  例：LlamaModel, QwenModel（完整的 forward 逻辑）            │
├─────────────────────────────────────────────────────────────┤
│  Layer 层                                                    │
│  Operation 的组合单元，定义通用大颗粒结构                    │
│  例：TransformerBlock（Attention + FFN + Norm 的组合）        │
├─────────────────────────────────────────────────────────────┤
│  Operation 层                                                │
│  最小成图单元，两种类型：                                    │
│  ● BaseOperation：ROPE、Self-Attention、RMSNorm 等基础算子   │
│  ● PluginOperation：用户自定义扩展算子                       │
└─────────────────────────────────────────────────────────────┘
```

**实际调用路径**：模型 forward → Layer 的 build_graph → Operation 的 atb 算子调用 → CANN kernel 执行

#### Step 3：调用 CANN 算子

```python
# 调用昇腾专用 FlashAttention（通过 ATB Python 绑定）
import _libatb_torch as atb

class ATBAttentionLayer(nn.Module):
    def forward(self, query, key, value, attention_mask, seq_len):
        # CANN FlashAttentionScore 融合算子（推理优化版本）
        output = atb.ops.flash_attention_score(
            query, key, value,
            real_shift=None,        # ALiBi 位置编码偏移，无则 None
            drop_mask=None,         # dropout mask，推理时为 None
            padding_mask=None,      # padding mask，PagedAttn 下为 None
            atten_mask=attention_mask,
            scale_value=self.scale, # 1/sqrt(head_dim)
            head_num=self.num_heads,
            input_layout="BSH",     # 布局：BSH/SBH/BSND/BNSD
            pre_tokens=65536,       # 可见的历史 token 数（通常设 max_seq_len）
            next_tokens=0,          # causal mask: 0（不看未来）
            keep_prob=1.0,          # dropout 保留率，推理固定为 1.0
            sparse_mode=0,          # 见下方 sparseMode 说明
        )
        return output
```

**aclnnFlashAttentionScore 关键约束（来自官方文档）**：

| 参数 | 类型 | 支持范围 |
|------|------|---------|
| query/key/value dtype | tensor | FLOAT16、BFLOAT16（推理选 BF16） |
| atten_mask dtype | tensor | BOOL 或 UINT8 |
| B (batch) | int | 1 ~ 2048 |
| N (heads) | int | 1 ~ 256 |
| S (seq_len) | int | 1 ~ 512K |
| D (head_dim) | int | 1 ~ 512 且须为 16/32 的倍数 |
| key/value shape | — | 必须与 query 的 B 一致，key 和 value shape 必须相同 |

**sparseMode 枚举（causal mask 的核心控制）**：

| 值 | 模式名 | 适用场景 |
|----|--------|---------|
| 0 | defaultMask | 使用 atten_mask 张量，最通用 |
| 2 | leftUpCausal | 下三角因果 mask，prefill 用 |
| 3 | rightDownCausal | 右对齐因果 mask |
| 4 | band | 滑动窗口（Mistral/Gemma3），配合 pre_tokens/next_tokens |
| 5 | prefix（非压缩） | prefix sharing 场景 |
| 6 | prefix（压缩） | prefix sharing 压缩版，B ≤ 32 |

**推理最佳实践**：
- prefill：`sparse_mode=2`（leftUpCausal），`atten_mask=None` 可省略显存分配
- decode：`sparse_mode=0`，`atten_mask` 传 None（单 token 无需 mask）
- 滑动窗口：`sparse_mode=4`，`pre_tokens=sliding_window`，`next_tokens=0`

### 6.9 图执行模式实战

> 图模式是昇腾推理性能调优的核心手段，MindIE-LLM 与 vllm-ascend 的图化方式有本质差异。本节聚焦**适配和调试时的实操要点**，技术原理详见 §13.7。

#### 6.9.1 MindIE / ATB 图模式

ATB 本身就是一套**图化推理编程模型**，模型不是"先写 PyTorch 再编译成图"，而是**直接用 ATB API 将算子组成图**。适配工程师需要理解 ATB 图的构建与执行生命周期：

```
构建期（Python import 时）
  └── atb.Graph.add_op(...)   ← 声明图的算子和连接关系

编译期（首次 forward 前）
  └── graph.compile()         ← 编译图拓扑，固定算子类型和连接
                                 不固定 shape（支持运行时动态 shape）

执行期（每次 forward）
  └── graph.execute(inputs)   ← 只更新输入 tensor，图结构不重建
```

**关键点**：ATB 图的"静"是**拓扑结构静**，而非 shape 静，同一张图可处理不同 seq_len 的请求，无需 CUDA Graph 那样的多档 bucket。

**图模式相关环境变量**：

```bash
# 开启 ATB 图内存复用（强烈推荐，可降低 20-30% 显存）
export ATB_LAYER_INTERNAL_TENSOR_REUSE=1

# 算子异步执行，提升多 layer 流水并行
export ATB_OPERATION_EXECUTE_ASYNC=1

# 如遇图执行异常，临时关闭图模式以隔离问题
export ATB_USE_GRAPH_MODE=0   # 退回单算子逐个执行（Eager 等价）

# 图结构可视化（调试用，输出 .dot 文件）
export ATB_DUMP_GRAPH=1
```

**MindIE Turbo 图优化**（MindIE 2.0+）：

MindIE Turbo 在 ATB 图基础上进一步执行**算子融合**（operator fusion），将相邻轻量算子合并为一个 CANN kernel，消除算子间的显存搬运：

```bash
# 在 MindIE Service config.json 中启用 Turbo
{
  "backendType": "atb",
  "turboConfig": {
    "enable": true             # 启用 Turbo 图优化
  }
}
```

典型融合：`RMSNorm + Add`（残差归一化）、`Linear + SiLU`（门控 FFN）合并为单 kernel，在 32B+ 大模型多卡高并发场景下吞吐提升最明显。

**适配时的图模式注意事项**：

1. **新增算子必须有 ATB Operation 对应**：若模型用了自定义算子，需先确认 ATB 支持（`atb.ops` 下是否有该算子），否则只能用 `PluginOperation` 接口包一层
2. **shape 约束检查**：ATB 图支持动态 shape，但部分算子有约束（如 FlashAttention 要求 `head_dim` 为 16/32 的倍数），违反约束会在 `compile()` 阶段报错而非运行时
3. **图调试优先用 Eager**：用 `ATB_USE_GRAPH_MODE=0` 关闭图模式，将错误定位到单算子粒度，确认正确后再开图模式验证整图

---

#### 6.9.2 vllm-ascend 图模式（ACLGraph）

vllm-ascend 的图模式机制对标 CUDA Graph，核心是**运行时捕获重放**：Warmup 时记录一遍 NPU 执行轨迹，推理时直接重放，消除每次 forward 的 CPU→NPU 调度延迟。

**cudagraph_mode 参数速查**：

| 值 | 含义 | Npugraph_ex | 适用场景 |
|----|------|------------|---------|
| `FULL` | 整个 forward（含 Attention）纳入 ACLGraph | ✅ 启用 | 纯 decode 批次，吞吐最优 |
| `FULL_DECODE_ONLY` | decode 批次走 FULL；含 prefill 时退回 PIECEWISE | ✅ 启用 | 高并发在线服务（推荐默认） |
| `PIECEWISE` | Attention 以 Eager 执行，FFN/Norm 等图化 | ❌ | prefill/decode 混合批次 |
| `FULL_AND_PIECEWISE` | 两套图都捕获，运行时动态切换 | ❌ | 通用场景，内存开销较大 |
| `NONE` | 不成图，全 Eager 执行 | ❌ | 调试、问题隔离 |

**v0.15+ 默认行为**：`FULL` + Npugraph_ex，NPUGraph EX 默认启用。

**启动配置示例**：

```python
from vllm import LLM

# 生产推荐（decode 为主的在线服务）
llm = LLM(
    model="Qwen/Qwen3-7B",
    device="npu",
    enforce_eager=False,            # 开启图模式（默认）
    # cudagraph_mode 由 vllm-ascend 内部管理，通过环境变量覆盖：
)

# 调试时强制 Eager
llm = LLM(model="...", enforce_eager=True)
```

```bash
# 通过环境变量精细控制图模式
export VLLM_ASCEND_CUDAGRAPH_MODE=PIECEWISE   # 覆盖默认图模式
export VLLM_ASCEND_ENABLE_NPUGRAPH_EX=0       # 临时关闭 Npugraph_ex 排查问题
```

**Shape Bucket 与流资源限制**：

ACLGraph 为每个 token 数档位各捕获一张图，需消耗 NPU stream 资源，上限约 **1800 张图**（NPU 总 stream 2048，保留 248）。PIECEWISE 模式每层还需额外 stream，层数多的模型（如 Qwen3-72B 80 层）需注意：

```bash
# 查看当前捕获的图数量（日志关键字）
grep "ACLGraph captured" vllm.log

# 若 stream 耗尽报错，减少 bucket 档位
export VLLM_ASCEND_GRAPH_BUCKET_SIZE=16    # 限制最大档位数
```

**Npugraph_ex 静态内核编译**（可选，长期在线服务推荐）：

```bash
# 启用静态内核预编译（首次启动多花几分钟到几十分钟）
export VLLM_ASCEND_STATIC_KERNEL_COMPILE=1

# 启动后检查是否生效
grep "static_kernel" op_statistic.csv
```

#### 6.9.3 图模式问题排查路径

无论 MindIE 还是 vllm-ascend，图模式问题的排查思路是一致的：

```
Step 1  先用 Eager 模式复现问题
  MindIE：   ATB_USE_GRAPH_MODE=0
  vllm-asc： enforce_eager=True

Step 2  确认 Eager 正确后，逐步开启图模式
  vllm-asc： 先试 PIECEWISE（Attention 仍 Eager，最安全）
             再试 FULL（整图，性能最好但约束最多）

Step 3  图模式特有问题
  ● 形状不匹配：检查 bucket 覆盖范围，确认实际 token 数在预热档位内
  ● OOM：图捕获期内存峰值高于 Eager，检查 max_num_batched_tokens 设置
  ● 精度下降：对比 Eager vs 图模式的中间 tensor（ATB_DUMP_ENABLE=1）
  ● 算子不支持图化：报错含 "cannot be captured"，需降级 PIECEWISE 或联系华为

Step 4  性能未提升
  检查是否真正进入图模式（日志搜索 "ACLGraph" / "ATB graph mode"）
  确认 decode 阶段 token 数足够小（token 数大时 NPU 执行时间主导，H2D 节省不明显）
```

### 7.3 显存/内存估算

```python
def estimate_model_memory_gb(
    num_layers, hidden_size, num_attention_heads, num_kv_heads,
    head_dim, intermediate_size, vocab_size,
    dtype_bytes=2,  # BF16=2, FP16=2, FP32=4
):
    # 词嵌入
    embed = vocab_size * hidden_size

    # 每层参数
    attn = (
        hidden_size * (num_attention_heads + 2 * num_kv_heads) * head_dim +  # QKV
        num_attention_heads * head_dim * hidden_size                          # O_proj
    )
    ffn = 3 * hidden_size * intermediate_size  # gate + up + down
    norm = 2 * hidden_size                     # 2 个 RMSNorm

    total_params = embed + num_layers * (attn + ffn + norm)
    return total_params * dtype_bytes / 1e9

# 示例：Qwen2.5-7B (BF16)
mem = estimate_model_memory_gb(28, 3584, 28, 4, 128, 18944, 152064)
print(f"模型显存：{mem:.1f} GB")  # ≈ 14 GB
```

### 8.1 量化方案选择矩阵

| 硬件 | 推荐方案 | 精度损失 | 速度提升 | 适用场景 |
|------|---------|---------|---------|---------|
| H100 (Hopper) | FP8 W8A8 | <0.5% | 1.5-2x | 生产首选 |
| A100 (Ampere) | AWQ INT4 + FP16 KV | 1-2% | 2-3x | 70B 单卡推理 |
| A100 (Ampere) | SmoothQuant W8A8 | <1% | 1.3-1.5x | 精度敏感场景 |
| 昇腾 910B | W8A8 INT8 | <1% | 1.5-2x | 昇腾生产部署 |
| 消费级 GPU | GGUF Q4_K_M | 2-3% | 3-4x | 个人/边缘部署 |

**决策原则**：先确定可接受精度损失阈值（如 <1%），再选方案；不要为了技术先进性选择过激的量化方案。

### 8.4 量化精度验证

```python
def verify_quantization_accuracy(orig_model, quant_model, tokenizer, test_prompts):
    for prompt in test_prompts:
        inputs = tokenizer(prompt, return_tensors="pt").to("cuda")
        with torch.no_grad():
            orig_logits = orig_model(**inputs).logits[0, -1]
            quant_logits = quant_model(**inputs).logits[0, -1]

        # KL 散度（越小越好，< 0.05 可接受）
        kl = F.kl_div(
            F.log_softmax(quant_logits.float(), dim=-1),
            F.softmax(orig_logits.float(), dim=-1),
            reduction="batchmean"
        ).item()

        # Top-1 一致率（> 90% 可接受，> 95% 优秀）
        match = (orig_logits.argmax() == quant_logits.argmax()).item()

        print(f"KL={kl:.4f}, Top1-match={match}, prompt='{prompt[:30]}...'")
```

### 8.6 FP8 量化（H100 / 昇腾 A3 专项）

FP8（E4M3 格式）是 H100 和昇腾新一代芯片原生支持的精度，在推理中能以几乎零精度损失换取约 1.5–2× 吞吐提升。

**与 INT8 的本质区别**：FP8 是浮点格式（有指数位），对模型权重中的大 outlier 天然友好，不需要 smooth quant 等预处理；INT8 是整数格式，对 outlier 敏感（LLaMA 系列有明显的 channel-level outlier）。

**何时选 FP8 而不是 AWQ/INT4**：
- 硬件支持 FP8（H100、Blackwell、昇腾 910C+）
- 精度要求高（FP8 损失通常 < 0.3%，INT4 损失 1–2%）
- 在线服务场景（FP8 无需 dequantize 额外 kernel，推理路径干净）

**工程注意事项**：
- 权重量化（W8）和激活量化（A8）需分别验证——先做 W8A16（只量化权重），确认精度，再做 W8A8（同时量化权重和激活）
- FP8 KV cache 是独立控制项，对长上下文场景（>64k token）建议单独测试精度影响
- H100 上 vLLM 通过 `quantization="fp8"` + `kv_cache_dtype="fp8"` 启用，两者都启用时内存节省最大，但需分别验证精度

### 8.7 GPTQ vs AWQ 的实战选择

市面上有大量 GPTQ 量化权重（HuggingFace 上最多），也有不少 AWQ 权重。不要默认"用现成的就好"，需要了解两者差异：

| 维度 | GPTQ | AWQ |
|------|------|-----|
| 量化对象 | 权重（逐层最优化） | 权重（保护激活 outlier 对应的 channel） |
| 校准数据 | 需要（128–512条） | 需要（同上） |
| 精度 | 略低于 AWQ（相同比特数） | 略高（channel-level scaling 保护 outlier） |
| 推理速度 | 取决于 kernel（ExLlamaV2 kernel 很快） | Marlin/GEMM kernel，A100 有专用加速 |
| 多硬件兼容 | 较广（llama.cpp/vLLM 均支持） | vLLM 支持好，llama.cpp 通过 GGUF 转换 |
| 推荐场景 | 需要 llama.cpp 部署、CPU 推理 | vLLM 在线服务、A100 GPU 部署 |

**校准数据的选择是量化精度的最大变量**——用任务相关数据远比通用 C4/WikiText 效果好。如果量化后在目标任务上精度下降明显，先换校准数据再考虑换量化方案。

### 8.8 昇腾 W8A8 量化工程要点

昇腾平台的 W8A8 量化走 vllm-ascend 路径（MindIE 2.0 后的官方分工），以下是区别于 GPU 平台的关键注意事项：

**量化粒度与 GPU 不同**：昇腾 W8A8 目前以 per-channel（权重）+ per-tensor（激活）为主，GPU 平台的 per-token 激活量化在昇腾上支持有限——适配时不要直接移植 GPU 的量化 config。

**量化工具链**：使用 `llm-compressor`（原 neural-compressor）生成 W8A8 量化权重，再通过 vllm-ascend 加载。工具链版本与 CANN 版本的兼容性是常见踩坑点，先查版本矩阵再安装。

**跳过量化层的判断**：在昇腾上，除了标准的 embedding / lm_head / norm / router 不量化之外，**MoE 的共享专家（shared expert）建议也跳过量化**——因为共享专家对所有 token 都生效，量化误差积累更快。

**精度验证的顺序**：先在单卡上用 BF16 和 W8A8 各跑一遍相同 prompt 的 logits 对比，确认 KL 散度在可接受范围（< 0.05），再做多卡 TP 验证，最后才做吞吐测试。多卡下量化问题与 TP 通信问题很难区分，一定要先单卡确认。

```python
def test_logits_alignment(ref_model, adapted_model, tokenizer, device):
    test_cases = [
        "The capital of France is",
        "def fibonacci(n):",
        "1 + 1 =",
    ]
    for prompt in test_cases:
        inputs = tokenizer(prompt, return_tensors="pt").input_ids.to(device)
        with torch.no_grad():
            ref_logits = ref_model(inputs).logits[0, -1].float()

        top5_ada = set(ada_logits.topk(5).indices.tolist())
        top5_overlap = len(top5_ref & top5_ada)

              f"argmax-match={ref_logits.argmax()==ada_logits.argmax()}")
```

### 9.3 逐层 Dump 对比（精度问题根因定位）

```python
# 当 logits 不对齐时，用 hook 捕获每层输出，找第一个发散层
def register_dump_hooks(model, dump_dict, prefix=""):
    hooks = []
    for name, module in model.named_modules():
        def make_hook(layer_name):
            def hook(module, input, output):
                if isinstance(output, torch.Tensor):
                    dump_dict[layer_name] = output.detach().cpu().float()
                elif isinstance(output, tuple) and isinstance(output[0], torch.Tensor):
                    dump_dict[layer_name] = output[0].detach().cpu().float()
            return hook
        hooks.append(module.register_forward_hook(make_hook(name)))
    return hooks

# 使用
ref_dumps, ada_dumps = {}, {}
hooks_ref = register_dump_hooks(ref_model, ref_dumps)
hooks_ada = register_dump_hooks(adapted_model, ada_dumps)

with torch.no_grad():
    ref_model(inputs)
    adapted_model(inputs)

# 找第一个发散层
for layer in sorted(ref_dumps.keys()):
    if layer not in ada_dumps:
        continue
    diff = (ref_dumps[layer] - ada_dumps[layer]).abs().max().item()
    status = "DIVERGE <<<" if diff > 0.01 else "ok"
    print(f"{layer}: max_diff={diff:.6f}  {status}")
```

## 十、常见坑点与调试指南

### 10.1 精度类问题速查表

| 症状 | 最可能根因 | 定位与解法 |
|------|-----------|-----------|
| Logits 量级对但数值偏 | `rope_theta` 不一致 | 严格从 config.json 读，不硬编码 |
| 前几层对，后面发散 | attention mask dtype 或数值错误 | 检查 causal mask：bool 还是 float，-inf 还是大负数 |
| decode 差 prefill 正常 | KV cache 写入/读取偏移 | 检查 block_size 计算和 slot 索引 |
| BOS/EOS 处理不同 | tokenizer 配置差异 | 检查 `add_bos_token`/`add_special_tokens` |
| 多卡比单卡精度差 | TP 切分后 all-reduce 精度损失 | 检查 TP 切分是否正确；开启 reduce_scatter 保护 |
| 同 prompt 不同批次结果不同 | temperature=0 时仍有随机性 | 检查 top-p/top-k 是否也为 greedy；检查 seed |
| 长序列（>8k）精度退化 | rope_scaling 未配置或配置错误 | 核对 rope_scaling 类型和参数 |

### 10.2 性能类问题速查表

| 症状 | 根因 | 解法 |
|------|------|------|
| GPU 利用率 < 60% | batch 太小；调度问题 | 增大 `max_num_seqs`；检查 continuous batching 配置 |
| prefill 慢 | FlashAttention 未生效 | 验证 FA 安装；检查 seq_len 对齐要求 |
| decode 慢 | KV cache 不足，触发 swap | 调低 `gpu_memory_utilization`（如 0.9→0.85）腾出 KV 空间 |
| 显存比预期高 | KV cache 预分配比例过高 | 调低 `max_num_seqs` 或 `max_model_len` |
| 量化后无加速 | AWQ 未用 Marlin kernel | 确认 `version="Marlin"`；检查 CUDA 版本 ≥ 11.8 |
| 昇腾比预期慢 | 未启用 CANN 图模式 | `torch_npu.npu.set_compile_mode(jit_compile=True)` |

### 10.3 昇腾 NPU 专项问题

| 症状 | 根因 | 解法 |
|------|------|------|
| `aclnnFlashAttentionScore` shape 报错 | head_dim 不满足对齐（须为 16/32 倍数）或超出约束（D > 512） | 检查 head_dim；必要时 padding 至对齐值 |
| FlashAttention 输出全为 NaN | BF16/FP16 混用，或 scale_value 传 0 | 统一 dtype 为 BF16；确认 scale=1/sqrt(head_dim) 非零 |
| 精度比 GPU 差 | BF16/FP16 混用，或 sparseMode 设置错误 | 统一使用 BF16；prefill 用 sparseMode=2，decode 用 0 |
| 多 NPU hang | HCCL 初始化失败，网卡未绑定 | 检查 HCCL 配置；设 `HCCL_WHITELIST_DISABLE=1`；确认网卡绑定 |
| 动态 shape 报错 | CANN 图模式不支持任意动态 shape | 启用 bucket 策略（固定几档 seq_len）；或切换 eager 模式 |
| 版本兼容问题 | CANN/torch_npu/PyTorch 版本不匹配 | 严格按版本矩阵（7.2 节），优先使用华为官方 Docker 镜像 |
| set_env.sh 未 source | ATB_SPEED_HOME_PATH 等变量未设置，atb 模块导入失败 | 按序 source 4 个 set_env.sh（见 6.4 节） |
| ATB 算子 `AICORE_INNER_PRODUCT` 报错 | 某层 Tensor 未对齐昇腾内存 alignment | 检查 weight 的 storage 是否连续（`.contiguous()` 处理） |
| 多卡推理显存不均 | TP 切分时部分 rank 接收了多余的 embedding weight | 检查 tie_word_embeddings 处理和 vocab parallel 分片逻辑 |

### 10.6 高频隐蔽 Bug 补充（来自生产经验）

以下坑点不在常见错误速查表中，但工程师碰到后往往排查数小时甚至数天。

#### Chat Template 不一致

**现象**：模型能跑，logits 对齐也没问题，但生成质量明显差于 HuggingFace，回答不跟指令、频繁重复、胡言乱语。

**根因**：`chat_template` 没有正确应用，或者直接用 raw prompt 而不是走 `tokenizer.apply_chat_template()`，导致系统提示词格式错误（缺少 `<|im_start|>system` 等特殊 token，或者多了额外空格）。

**经验**：任何 Instruct 模型的测试，必须用 `tokenizer.apply_chat_template(messages, add_generation_prompt=True)` 构造输入，绝不手拼格式字符串。不同系列模型的 chat template 差异很大（Qwen 的 im_start/im_end、LLaMA3 的 `<|begin_of_text|>` token），搞混一个就会全部出错。

---

#### attention mask 的 dtype 和数值

**现象**：prefill 正常，decode 阶段 logits 逐渐发散，越长越烂。

**根因**：causal attention mask 传的是 `-1e9` 而非 `-inf`（或传的是 `0/1` bool 而框架期望 `0/-inf` float）。在 softmax 之前，masked 位置必须是 `-inf` 才能保证 softmax 后精确归零；`-1e9` 在 BF16 下会被截断为 `-inf`，但在部分精度实现里不会，导致 masked 位置有微小非零权重，长序列下累积发散。

**经验**：推荐统一用 `torch.finfo(dtype).min`（该精度的最小有限值），而非魔法数字。

---

#### TP 下 vocab 并行的边界 token

**现象**：`tp=1` 正确，`tp=2` 时输出乱码，特别是句子末尾的特殊 token（EOS、PAD）。

**根因**：`VocabParallelEmbedding` 和 `ParallelLMHead` 按 vocab_size 切分，但 vocab_size 不整除 tp_size 时，最后一个 rank 会持有一段"填充"区域的 token id。如果 lm_head 的 logits 在 gather 时没有正确 mask 掉填充区域，top-k 采样可能选到 padding token id，输出乱码。

**经验**：确认框架的 `VocabParallelEmbedding` 实现有 vocab 边界 masking；换 tp_size 时先测 EOS token 是否能正常生成（输出不该提前截断也不该无限生成）。

---

#### 量化后的 outlier 层导致精度崩溃

**现象**：量化后大多数 benchmark 变化不大，但某一类任务（如代码生成、数学推理）精度骤降 10–20%。

**根因**：模型中有 1–2 个"outlier 层"（activation 数值范围远大于其他层），这些层量化误差极大，而这些层恰好对特定任务至关重要。

**经验**：量化前先做激活统计分析（per-layer 的 activation max/std），找出 top-5 异常层，把这些层加入 skip list 保持 FP16。通常只需跳过 2–3 层，整体显存增加可忽略，但精度恢复显著。

---

#### PP 多 stage 的 KV cache 漏初始化

**现象**：PP > 1 时，模型前几步输出正常，随后某个 stage 输出全零或 NaN，重启后随机复现。

**根因**：PP 中间 stage 在初始化 KV cache 时，block 数量按全局 `max_num_seqs × max_model_len` 计算，但实际分配在该 stage 对应的层数上。若层数计算有误（如 MoE 层漏计或 embedding 层多计），导致某 stage KV cache 块不够用，产生越界写入。

**经验**：PP 适配后立刻做"跑满 KV cache"压力测试（`max_num_seqs` 满并发 + `max_model_len` 长输入），不要只测低并发短序列就上线。

---

#### Tokenizer 的 `legacy` 模式

**现象**：从同一模型目录加载，不同版本 transformers 的 tokenization 结果不一致（token 数目差 1–2 个，或某些词 BPE 切法不同）。

**根因**：部分老版本模型（LLaMA1/2、早期 Mistral）的 tokenizer 有 `legacy=True/False` 开关，新版 transformers 默认值会变，导致空格处理、BOS 插入等行为改变。

**经验**：在工程代码中显式指定 `AutoTokenizer.from_pretrained(..., legacy=False)`（或 `True`，以官方 README 为准），不要依赖默认值。Golden reference 建立后锁定 transformers 版本。

### 12.2 核心推理优化技术现状

#### 12.2.1 Prefill-Decode 分离（PD Disaggregation）

PD 分离已从实验性功能变为**生产标准**，DeepSeek、Meta、LinkedIn 均在生产环境运行。

**核心动机**：
- Prefill 阶段：计算密集（矩阵乘法），受限于 FLOPS
- Decode 阶段：内存密集（KV cache 读取），受限于带宽
- 两者混部会互相干扰，导致两个阶段都达不到最优

**当前挑战**：KV cache 搬运是瓶颈——每 token 约 327KB（按 7B 模型估算），需要足够快的互联带宽（NVLink / RDMA）才能不让 Decode worker 等待

**适配影响**：新模型适配时需确认 KV cache 的 layout、dtype、block_size 与 PD 两侧一致

#### 12.2.2 投机解码（Speculative Decoding）

投机解码已进入**主流框架标配**，生产环境可实现 **2-3x** 延迟降低。

**主要方案演进**：

| 方案 | 原理 | 接受率 | 适配要点 |
|------|------|--------|---------|
| 独立 Draft 模型 | 小模型生成 5-8 个候选 token，目标模型并行验证 | 60-70% | 需维护 draft 模型与目标模型的 vocab/tokenizer 对齐 |
| EAGLE / EAGLE-2 | Draft 头直接复用目标模型特征，集成在目标模型内 | ~80% | 需在目标模型上附加 1-2 层 draft 头，适配量较小 |
| Medusa | 目标模型添加多个并行 draft 头，无需独立模型 | 70-75% | 需在 load_weights 中处理额外 head 的权重加载 |
| MTP（Multi-Token Prediction） | 训练时直接预测多 token，推理时自带投机能力 | 取决于模型 | DeepSeek V3 内置，适配时需处理 MTP head |

**趋势**：EAGLE 类方案因无需独立 draft 模型而成为首选；MTP 头作为训练时对齐机制正在成为新模型的标配设计。

#### 12.2.3 KV Cache 优化技术

KV cache 是长上下文推理的核心瓶颈，形成了多个互补的优化方向：

| 技术方向 | 代表方法 | 效果 | 适配影响 |
|---------|---------|------|---------|
| **量化压缩** | KVQuant（INT4/FP8） | 8x 压缩，支持 1M token | 需确认 attention 算子支持量化 KV 输入 |
| **语义压缩/驱逐** | RocketKV、ChunkKV | 16-20x 压缩比 | 需修改 KV cache 管理逻辑 |
| **前缀缓存** | RadixAttention（SGLang）、vLLM prefix cache | 多轮对话 TTFT 大幅降低 | 模型 forward 需支持 cache hit 跳过 |
| **磁盘卸载** | KVSwap | 支持超长上下文单卡推理 | 需应用层感知 KV tier（显存 / 内存 / SSD） |

**长上下文趋势**：主流模型上下文已达 128k-1M tokens，KV cache 管理正成为适配工作的独立专题，不再是边缘问题。

#### 12.3.1 当前主流架构（生产 Top 5）

截至 2026 年，以下模型系列占据生产推理工作负载的主体：

### 12.4 量化与压缩技术演进

#### 量化方案技术路线图

#### FP4 时代：Blackwell 带来的范式转变

NVIDIA Blackwell (B200) 引入原生 FP4 支持，形成两种标准：

| 格式 | Block Size | Scale 类型 | 精度 | 框架支持 |
|------|-----------|-----------|------|---------|
| **NVFP4** | 16 elements | E4M3 per-block + FP32 per-tensor（两级缩放） | 更高 | TensorRT-LLM 0.17+ |
| **MXFP4** | 32 elements | E8M0 shared scale（OCP MX 标准） | 标准 | 跨厂商兼容 |

**B200 性能提升**：相比 H100，B200 在 LLM 推理上约提升 **15x**（离线 batch），FP4 进一步将每 token 成本压缩至约 $0.02/M tokens（相比 Hopper 下降 4.5x）。

**模型适配影响**：FP4 量化需要 Quantization-Aware Distillation（QAD）辅助精度恢复，不能直接用 PTQ 方案；适配新模型时需同时规划 FP8（生产稳定）和 FP4（最优性能）两套量化路径。

#### 量化技术趋势

1. **QAT 重要性上升**：激进量化（W4A4/FP4）需要 QAT，纯 PTQ 在精度上难以达标
2. **KV Cache 专用量化**：KV 的量化策略与权重量化独立，FP8 KV 已成 H100 标配
3. **结构化稀疏性（2:4 Sparsity）**：与量化组合，Ampere+ 原生支持，适配时权重需转换格式
4. **越来越多框架支持统一量化 API**：llm-compressor（vLLM 官方工具）统一处理 GPTQ/AWQ/FP8/FP4

### 12.5 算子编译与内核优化趋势

#### 从手写 CUDA 到编译器生成

LLM 内核开发正经历从**手工优化**向**编译器辅助生成**的范式转变：

| 阶段 | 代表技术 | 特点 |
|------|---------|------|
| **手工 CUDA** | FlashAttention 1/2 | 极致性能，但每个变体需重写 |
| **Triton** | 现有大多数 vLLM kernel | Python 写 GPU kernel，易维护 |
| **编译器生成** | FlexAttention + torch.compile | 注意力变体自动生成 Triton kernel |
| **JIT 生成** | FlashInfer JIT | 根据运行时参数生成最优 kernel |

#### 关键技术

**FlexAttention**（PyTorch 2.5+）：通过 `torch.compile` 自动将任意注意力变体（SWA、ALiBi、文档 mask 等）编译为优化 Triton kernel，**适配新注意力机制时不再需要手写 kernel**，工程成本大幅降低。

**FlashInfer**：生产级 LLM serving kernel 库，支持：
- PagedAttention / Ragged KV Cache
- 所有注意力阶段（prefill/decode/append）的优化
- JIT 编译，根据 head_dim/dtype/注意力变体自动生成最优 kernel
- 已成为 SGLang 默认 attention 后端

**torch.compile 在 vLLM 中的地位**：vLLM V1 将 torch.compile 作为核心优化路径，负责 norm/projection/FFN 的自动融合，与手写 attention backend 协同，CUDAGraph 与 compile 进一步协作减少 kernel launch 开销。

**未来方向**：LLM 感知的编译器（"LLM == 编译器"趋势，即用 LLM 自动生成 kernel）正在研究阶段，TVM Relax、IREE 等也在探索跨硬件统一编译。

### 12.7 新兴适配挑战

#### 12.7.1 多模态模型适配

VLM（Vision-Language Model）适配在传统 LLM 适配之上新增几个独特挑战：

| 挑战 | 说明 | 当前方案 |
|------|------|---------|
| **视觉 token 爆炸** | 一张高分辨率图产生 4k+ token，输入长度剧增 | 视觉 token 压缩（pooling/pruning）减少到 256-1024 |
| **动态分辨率** | 不同尺寸图像产生不同 token 数，破坏 static shape | Padding 或 Sequence Packing 处理不等长输入 |
| **跨模态注意力** | 视觉与文本的注意力模式不同 | 多数 VLM 复用 causal LLM attention，视觉 token 置于前缀 |
| **多模态 KV Cache** | 图像 KV 占用大，复用率低 | 前缀缓存对图像重复使用场景有效 |

**框架支持**：vLLM Omni 是目前多模态支持最广泛的推理框架，适配新 VLM 时可复用其 MultiModalProcessor 接口。

#### 12.7.2 推理时扩展（Inference-Time Scaling）

2025 年最重要的新趋势之一：**用更多推理计算提升模型输出质量**。

- **Chain-of-Thought / Extended Thinking**：模型生成超长推理链（1k-100k tokens），对长上下文推理性能要求极高
- **Best-of-N 采样**：并行生成 N 个候选，选最优，对批处理效率和输出多样性要求高
- **Verifier-in-the-Loop**：外部验证器（数学、代码执行）与生成过程交互，适配时需支持流式输出与中断重进

**对适配的影响**：`max_output_length` 的上限从 2k 扩展到 32k+，decode 阶段性能优化的权重大幅上升；KV cache 容量成为系统瓶颈。

#### 12.7.3 大规模 MoE 专家并行（Wide EP）

DeepSeek V3/R1（256 专家，每 token 激活 8）的生产部署推动了 Wide Expert Parallelism 的成熟：

- **当前规模**：96 卡 H100 部署，52k input tokens/sec，22k output tokens/sec（PD+EP 组合）
- **通信挑战**：token routing 的 all-to-all 通信在跨节点时是主要瓶颈，需要高速互联（InfiniBand / HCCS）
- **MoE + PD 分离**：MegaScale-Infer 将 attention 和 FFN（专家）模块独立分离，独立扩展，是 MoE 推理的前沿方向
- **适配工作量**：Wide EP 下每 rank 只持有少量专家，权重加载、路由逻辑、all-to-all 通信均需针对性实现

### 12.8 技术选型建议矩阵

根据上述技术现状，给出不同场景下的技术选型建议：

#### 场景一：新模型快速上线（最常见）

```
目标：3-7 天内完成适配，跑通推理
路线：HuggingFace 验证 → vLLM 适配 → 精度回归测试
量化：BF16 起步，后续按需加 FP8（GPU）或 INT8（昇腾）
并行：单卡先跑通，多卡按需扩展
```

#### 场景二：生产性能优化（GPU, NVIDIA）

```
目标：最大化吞吐，最小化成本
路线：TensorRT-LLM 或 vLLM + torch.compile
量化：H100 → FP8 W8A8；B200 → NVFP4
优化：PD 分离 + FlashInfer backend + CUDAGraph
KV Cache：FP8 KV Cache + 前缀缓存
大模型：Wide EP + PD 分离（DeepSeek 类 MoE）
```

#### 场景三：昇腾 NPU 国产化适配

```
目标：在昇腾上达到 GPU 80% 以上性能，通过自主可控审查
路线：vllm-ascend（快速验证）→ MindIE-LLM ATB（性能优化）
量化：W8A8 INT8（主流），关注 CANN 8.x FP8 支持进展
并行：TP=8 单节点优先，多节点需验证 HCCL 稳定性
未来：关注 910D/950 对 FP8 的原生支持
```

#### 场景四：长上下文 / 多模态

```
目标：支持 32k-1M tokens 或多模态输入
路线：rope_scaling 配置 → KV Cache 量化（FP8 KV）→ 视觉 token 压缩（VLM）
框架：vLLM Omni（多模态最广）或 SGLang（前缀缓存最强）
技术预判：关注 MLA 普及（天然 KV 压缩）和 FlexAttention 降低 SWA 适配成本
```

## 十三、MindIE-LLM 与 vllm-ascend 技术路线深析

### 13.1 昇腾推理框架双轮格局

昇腾 NPU 上的 LLM 推理形成了两条平行但互补的技术路线：

| 维度 | MindIE-LLM | vllm-ascend |
|------|-----------|-------------|
| **归属** | 华为官方自研 | vLLM 社区 + 华为共建 |
| **仓库** | Ascend/MindIE-LLM（闭源核心 + 开放接口） | vllm-project/vllm-ascend（完全开源） |
| **底层引擎** | ATB（Ascend Transformer Boost）深度集成 | vLLM V1 Engine + CANN/ATB 算子适配 |
| **API 兼容性** | OpenAI 兼容接口，独立配置体系 | OpenAI 兼容，与 vLLM 原生 API 完全一致 |
| **版本节奏** | 跟随 CANN/NNAL 版本发布，约每季度一个大版本 | 跟随 vLLM 版本发布，约 4-6 周一个版本 |
| **核心优势** | 多卡/大模型吞吐最优，ATB 图融合深度优化 | 生态兼容性最广，快速跟进社区新特性 |
| **主要用户** | 企业级高吞吐生产环境，昇腾深度绑定场景 | 开发者快速迁移，多框架混部，社区用户 |

#### 13.2.2 三大技术阶段分析

**阶段一（1.0.RC1 → 1.0.0）：基础能力建立**

- 核心目标：证明昇腾平台可以运行主流 LLM，提供基本的生产部署能力
- 技术重点：PagedAttention、Continuous Batching 在 ATB 框架上落地
- 典型限制：上下文长度受限、多卡场景不稳定、配置复杂度高
- 里程碑意义：昇腾推理从"学术验证"走向"企业可用"

**阶段二（2.0.RC1 → 2.1.RC2）：性能优化与生态协同**

- 核心目标：缩小与 NVIDIA 平台的性能差距，建立与 vllm-ascend 的明确分工
- 技术重点：
  - **MindIE Turbo**：算子融合加速插件，通过 CANN 图编译实现 operator fusion，解决多卡大模型吞吐差距问题
  - **Context Parallel (CP)**：序列维度并行，将长序列按 Ring-based KV 分配到多卡，降低首 token 延迟
  - **Expert Parallel (EP)**：MoE 场景下专家分布在不同卡，DeepSeek V3/R1 专属优化路径
  - **W8A8 量化分工**：量化推理能力明确移交 vllm-ascend 维护，MindIE 聚焦高精度吞吐场景
- 战略意义：形成"MindIE 做性能极限，vllm-ascend 做生态兼容"的明确分工

**阶段三（2.2.RC1+）：服务化体系完善**

- 核心目标：构建完整推理服务平台，覆盖 LLM、多模态、边缘部署全场景
- 技术重点：
  - **MindIE Motor**：通用推理服务化框架，解耦模型推理与服务调度，支持主备倒换、Pod 重调度，具备电信级可靠性
  - **MindIE SD**：独立的视图生成（Stable Diffusion / DiT 系列）推理框架，与 LLM 推理体系并列
  - **KV Cache 池化**：跨请求 KV Cache 共享，提升 Prefix Cache 命中率
  - **PD 分离**：缩P保D（Prefill 缩容时保证 Decode 不中断）的高可用能力

#### 13.2.3 MindIE 产品组件全景

MindIE 已从单一推理引擎演变为多组件推理平台：

```
MindIE 平台
├── MindIE LLM          ← 核心推理引擎（ATB 三层架构）
│   ├── Operation 层     ← CANN 算子封装（FlashAttention, Matmul...）
│   ├── Layer 层         ← Transformer 子模块（Attention, FFN...）
│   └── Model 层         ← 完整模型推理图
├── MindIE Service (Motor) ← 服务化框架（HTTP/gRPC, 负载均衡, 高可用）
├── MindIE Turbo         ← 图模式加速插件（算子融合, 内存优化）
├── MindIE SD            ← 视图生成推理框架（Stable Diffusion 系列）
└── vllm-ascend          ← 官方推荐的开源推理引擎接口（2.0+ 后协同）
```

### 13.4 性能对比与适配场景分析

#### 13.4.1 实测性能格局（基于社区公开数据）

在昇腾 910B（Atlas 800I A2）平台上，两个框架在不同场景下各有优劣：

**单卡小模型（7B-14B，BF16）：**

vllm-ascend 在 TTFT（首 token 延迟）上通常优于 MindIE，单算子模式在小并发下调度开销更小。

**多卡大模型（32B+，4-8 卡 TP）：**

MindIE 通过 ATB 图模式融合算子，在吞吐量上具有明显优势（文献数据：DeepSeek-R1 8 卡场景 MindIE 吞吐高于 vllm-ascend 约 20-30%）。MindIE Turbo 的算子融合消除了大量内存 copy，在高并发下更明显。

**图模式均衡后：**

vllm-ascend 的 ACLGraph（Graph Mode）上线后，两者性能差距大幅收窄。对于大多数模型，NPUGraph EX 默认启用后 vllm-ascend 已经能达到接近 MindIE 的吞吐。

```
      │     └── 是 → MindIE（ATB 图融合在高并发大模型场景优势明显）
      └── 快速适配新模型、跟进社区新特性、混部环境？
```

#### 13.5.2 不同工程场景下的推荐策略

**场景 A：新模型快速适配与验证**
- 推荐：**vllm-ascend**
- 理由：注册接口与 vLLM 完全一致，GPU 开发的适配代码几乎可直接复用；社区模型覆盖最广，参考案例多；CI 精度对比系统完善
- 注意：Graph Mode（ACLGraph）需要额外确认模型是否支持图编译

**场景 B：数据中心大模型高吞吐生产部署**
- 推荐：**MindIE-LLM + MindIE Turbo**
- 理由：ATB 底层图融合优化，高并发大模型（32B+）场景具有明显吞吐优势；MindIE Motor 提供电信级服务可靠性
- 注意：配置体系独立，运维成本高于 vllm-ascend；需关注 CANN 版本锁定问题

**场景 C：DeepSeek / Qwen3 等重点模型极致优化**
- 推荐：**两者均可，按模型规模切分**
- 7B-14B Dense：vllm-ascend（低延迟优势）
- 32B+ MoE：MindIE（吞吐优势）+ vllm-ascend W8A8 量化路径

**场景 D：RLHF / 强化学习训推一体**
- 推荐：**vllm-ascend**
- 理由：与 verl、OpenRLHF、LLaMA-Factory 的集成在 vllm-ascend 路线图中有明确规划和落地；MindIE 在此方向尚无成熟方案

**场景 E：边缘 / 端侧推理（Atlas 500 / Atlas 200I DK）**
- 推荐：**MindIE（原生）**
- 理由：vllm-ascend 目前不支持这类边缘硬件；MindIE 针对低功耗、低带宽环境有专项优化

### 13.6 两条路线的战略收敛趋势

#### 13.6.1 分工清晰化（2025 年已落地）

MindIE 2.0 后，华为明确将部分技术能力"迁移至 vllm-ascend 维护"，包括：
- W8A8 量化推理能力
- 高性能算子 enable 的能力（通过 Turbo 插件形式对接）

这标志着华为官方认可"双轨并行"策略：MindIE 做深度硬件优化，vllm-ascend 做开放生态接口。

#### 13.6.2 共同依赖 CANN/NNAL 底层

两条路线均基于同一套硬件软件栈：

```
应用层    MindIE-LLM / vllm-ascend
          ↓
框架层    ATB（Ascend Transformer Boost）/ NNAL 算子库
          ↓
运行时    CANN（Compute Architecture for Neural Networks）
          ↓
硬件      昇腾 NPU（910B / 910C / 910D / 920 / 950）
```

这意味着：
1. CANN 版本升级带来的算子性能提升，两条路线均可受益
2. 新硬件支持（910C/910D/950）通常先在 CANN 层落地，两个框架跟进节奏相近
3. 底层 ATB 的 bug 会同时影响两条路线

#### 13.6.3 vllm-ascend 演进关键节点预判

根据公开路线图与当前状态，未来 12-18 个月的关键节点：

| 时间预估 | 关键能力 | 意义 |
|---------|---------|------|
| 2025 Q4-2026 Q1（已基本达成） | V1 引擎 + ACLGraph 生产就绪 | 性能差距大幅收窄，选型压力减少 |
| 2026 Q1-Q2（进行中） | 多模态 VLM 完整支持 | 覆盖视觉推理场景，减少对 MindIE SD 的依赖 |
| 2026 Q2-Q3 | Ascend 910D / 950 生产级支持 | 新硬件快速迁移路径确立 |
| 2026 下半年 | LoRA 生产就绪 | 微调推理一体化场景打通 |
| 持续演进 | MTP / PD 分离 / EPLB 成熟 | 与 MindIE 功能全面对齐，差距收敛到特定边缘场景 |

#### 13.6.4 工程师的战略判断

**短期（0-12 个月）**：两者能力差距仍存在，需按场景选型。新模型适配首选 vllm-ascend 以缩短周期，大规模生产部署评估 MindIE 的性能增益是否值得运维成本。

**中期（12-24 个月）**：随着 vllm-ascend ACLGraph 成熟和 MindIE 技术迁移持续，两者性能差距将进一步收敛。主要差异将集中在：边缘部署（MindIE 独有）、高可用服务化（MindIE Motor）、开放生态（vllm-ascend）。

**长期（2026+）**：昇腾 NPU 在推理生态上的主要战场将是"与 NVIDIA 生态的全面竞争"，双轨策略（官方自研 + 社区开源）本身是有意为之的生态覆盖策略，两条路线均会长期维护。

### 13.7 昇腾图执行模式技术分层

> 昇腾平台上"图模式"并非一个单一概念，而是一个由多层技术构成的体系。工程师必须理解各层次的定义与边界，才能准确判断性能瓶颈并选择适配路径。

#### 13.7.1 全景：四种执行模式对比

| 执行模式 | 中文名 | 成图方式 | 形状约束 | 控制流 | 典型场景 |
|---------|-------|---------|---------|--------|---------|
| **Eager（单算子模式）** | 单算子逐个下发 | 无图，逐算子 CPU→NPU | 完全动态 | 支持 | 调试、极小批次 |
| **ACLGraph（类 CUDAGraph）** | 捕获重放 | 运行时捕获 forward 完整图 | 静态（多档 bucket） | 受限（无分支） | vllm-ascend 默认 decode 路径 |
| **torchair（整图下沉）** | torch.compile 整图 | 编译期将 PyTorch FX 图 lowering 到 Ascend GE | 静态为主，有限动态 | 受限 | 结构固定模型、训练推理一体 |
| **ATB Graph（MindIE 原生）** | ATB 图化推理 | 模型以 ATB API 直接描述为计算图 | 动态支持（图拓扑不变） | 有限支持 | MindIE-LLM 全系场景 |

---

#### 13.7.2 Eager 模式（单算子模式）

**执行机制**：CPU 宿主端逐个将算子（op1 → op2 → op3 …）下发到 NPU 执行，每次下发均有 host-to-device (H2D) 调度延迟。

**核心问题 —— Host Bound**：

```
CPU:  [launch op1] [wait] [launch op2] [wait] [launch op3] ...
NPU:  [   op1   ] [idle]  [   op2   ] [idle]  [   op3   ] ...
                   ↑ 这段 idle 是 H2D 调度开销，积累后严重拖慢吞吐
```

**适用场景**：
- 调试期定位精度问题（逐 layer 检查 tensor）
- 模型结构存在复杂动态控制流无法图化时的回退方案
- 极小批次（token 数很少时 NPU 执行时间本身短，H2D 开销占比可接受）

**启用方式（vllm-ascend）**：`enforce_eager=True` 或 `cudagraph_mode="NONE"`

---

#### 13.7.3 ACLGraph（类 CUDAGraph 捕获重放）

ACLGraph 是 vllm-ascend 的**默认图执行路径**，对标 NVIDIA 的 CUDAGraph，是昇腾软件栈未来的主要演进方向。

**执行机制**：
1. **Warmup 阶段**：以固定形状运行一遍 forward，CANN 运行时记录所有算子及其内存地址 → 生成静态图
2. **Replay 阶段**：真实推理时，CPU 只需发出一次"执行图"指令，NPU 自行连续执行所有算子，彻底消除 H2D 调度空洞

**形状约束与 Bucket 策略**：

ACLGraph 要求图的输入 shape 与捕获时完全一致。LLM 推理 token 数是动态的，通过**多档预热**解决：

```
捕获多张静态图：graph_1[token=1]  graph_4[token=4]  graph_16[token=16] ...
推理时选图：    实际 token=3 → padding 到 4 → replay graph_4
              实际 token=5 → padding 到 16 → replay graph_16
              实际 token > 上限 → 回退 Eager 模式
```

多档图捕获消耗 NPU stream 资源，**上限约 1800 张图**（总 stream 2048，保留 248 个）。

**Piecewise（分段图）vs Full（整图）**：

LLM 的 Attention 层在混合批次（prefill token + decode token 同批）时行为复杂，难以整体图化：

| 子模式 | 机制 | Attention 执行方式 | 适合场景 |
|-------|------|--------------------|---------|
| **FULL** | 整个 forward（含 Attention）全部纳入 ACLGraph | 图内执行 | 纯 decode 批次 |
| **PIECEWISE** | Attention 以 Eager 执行，Attention 之外的计算（FFN、残差、LayerNorm…）图化 | Eager | 混合 prefill/decode 批次 |
| **FULL_DECODE_ONLY** | 纯 decode 批次走 FULL；出现 prefill 时退回 Piecewise | 按批次动态选择 | 高并发以 decode 为主 |
| **FULL_AND_PIECEWISE** | 编译时生成两套图，运行时按批次切换 | 动态选 | 通用服务场景 |

**vllm-ascend 默认行为（v0.15+）**：`cudagraph_mode="FULL"` + Npugraph_ex 启用。

---

#### 13.7.4 Npugraph_ex（编译时 FX 图优化层）

Npugraph_ex **不是独立的图执行模式**，而是运行在 ACLGraph **之前**的编译时优化层，两者组合形成完整的图执行流水：

```
Python forward()
    ↓
[Npugraph_ex] FX Graph Pass：算子融合（add+rms_norm → 单 kernel）
    ↓
[ACLGraph] 运行时捕获融合后的图 → Replay
```

**核心作用**：将多个相邻轻量算子合并为一个 kernel，减少 kernel launch 次数。典型融合案例：

- `add + rms_norm` → 单融合 kernel（RMSNorm 后加残差极常见）
- `linear + activation` → 融合线性激活
- 跨 layer 常量折叠

**启用条件**：仅在 `cudagraph_mode` 为 `FULL` 或 `FULL_DECODE_ONLY` 时自动启用，`PIECEWISE` 模式下不生效。

**静态内核编译（Static Kernel Compilation）**：Npugraph_ex 的可选增强，在 Warmup 阶段预编译固定 shape 的算子二进制。默认关闭；启用后首次启动多花数分钟到数十分钟，但后续推理无额外开销，适合长期在线服务。

---

#### 13.7.5 torchair / 整图下沉

torchair 是 `torch_npu` 提供的 `torch.compile` 后端，走的是**完全不同的技术路线**：

**执行机制**：

```
Python model forward()
    ↓
torch.compile(backend="torchair")
    ↓
PyTorch FX 图追踪（tracing） → 捕获完整计算图
    ↓
torchair 将 FX 图 Lower 到 Ascend GE（Graph Engine）格式
    ↓
Ascend GE 编译优化（算子融合、内存规划、图切分）
    ↓
整张图作为单一 GE 图下沉到 NPU 执行（整图下沉）
```

**与 ACLGraph 的根本差异**：

| 对比维度 | ACLGraph | torchair（整图下沉） |
|---------|----------|-------------------|
| **成图时机** | 运行时捕获（先跑一遍，记录执行轨迹） | 编译期静态追踪（AOT 编译） |
| **控制流** | 不支持（图内无分支，分支需 Piecewise 绕过） | `reduce-overhead` 模式同样不支持；`max-autotune` 部分支持 |
| **动态 shape** | Bucket 多档预热 | 有限支持，需 `dynamic=True` 配合，约束较多 |
| **图边界** | 可 Piecewise 拆分（Attention 单独处理） | 整图下沉灵活性低，调试困难 |
| **优化深度** | Npugraph_ex 做 FX pass 融合 | GE 编译器做全图优化（更深但更重） |
| **启动开销** | Warmup 若干次 forward | 首次编译时间长（分钟级） |
| **调试友好度** | 中等（Piecewise 回退 Eager 可逐层检查） | 低（整图黑盒，难插断点） |
| **主要用途** | vllm-ascend 推理默认路径 | MindIE 训练/推理一体场景，torch.compile 适配 |

**整图下沉的核心价值**：由于整张图交给 GE 编译器统一规划，可做**跨层内存复用**（消除中间 tensor 的显式分配）、**更激进的算子融合**、**流水线并行**等，在结构高度固定的场景（固定 seq_len 的离线批处理）可以获得极致性能。

**LLM 推理的挑战**：在线 LLM 推理 seq_len 和 batch_size 动态变化，整图下沉需要为每个 shape 组合重编译，或依赖动态 shape 机制（性能损失明显），因此 torchair 在 vllm-ascend 中用于 **torch.compile 集成实验**而非默认路径。

---

#### 13.7.6 ATB Graph（MindIE 原生图模式）

ATB（Ascend Transformer Boost）是 MindIE 的底层推理引擎，其图模式与上述路线**本质不同**——它不是"先写 PyTorch 代码再编译/捕获成图"，而是**直接用 ATB API 把模型描述为计算图**：

```
开发者直接调用 ATB API 构建图：
  graph = atb.Graph("MyModel")
  graph.add_op(atb.ops.LinearOp, ...)
  graph.add_op(atb.ops.FlashAttentionOp, ...)
  graph.add_op(atb.ops.RmsNormOp, ...)
  ...
  graph.compile()       ← 编译期固定图拓扑
  graph.execute(inputs) ← 运行时只更新输入数据，图结构不变
```

**关键特性**：
- **图拓扑编译时确定，输入数据运行时动态**：与 CUDAGraph/ACLGraph 的 shape 完全静态不同，ATB 图支持同一张图处理不同 seq_len（通过内部动态 shape 机制），不需要多档 bucket
- **三层抽象**：Operation（单算子） → Layer（Transformer 子层） → Model（完整模型），图在 Model 层统一编译，内部子图自动融合
- **MindIE Turbo 增强**：在 ATB 图基础上进一步做算子融合、内存 zero-copy 优化，消除相邻算子之间的显存搬运，是 MindIE 高吞吐的核心来源

**ATB 图模式的适配代价**：需要按 ATB API 重新实现模型（不复用 Hugging Face 代码），适配工作量大，但换来的是**对昇腾硬件的深度优化**。这也是 MindIE 在 32B+ 大模型多卡场景下性能优于 vllm-ascend 的根本原因。

---

#### 13.7.7 图模式选型总结（昇腾推理场景）

```
新模型快速上线 / 调试精度
  → Eager 模式（enforce_eager=True）

vllm-ascend 标准在线推理（推荐路径）
  → ACLGraph FULL + Npugraph_ex（默认，decode 为主）
  → ACLGraph PIECEWISE（prefill/decode 混合批次）
  → ACLGraph FULL_AND_PIECEWISE（通用高并发服务）

极致性能 / 离线固定 shape 批处理
  → torchair 整图下沉（静态 shape，结构高度固定）
  → Static Kernel Compilation（Npugraph_ex 增强，长期在线服务）

MindIE 原生 / 最高多卡吞吐
  → ATB Graph（模型按 ATB API 实现，MindIE Turbo 加速）
```

**一句话总结各层定位**：
- **Eager**：不成图，随时可跑，随时可调，性能最差
- **ACLGraph**：捕获重放，接近 CUDAGraph，动态 shape 靠 Bucket，是 vllm-ascend 的现实最优解
- **Npugraph_ex**：ACLGraph 的编译前置优化，融算子减 launch 次数，透明叠加
- **torchair/整图下沉**：编译期追踪 → GE 全图优化，适合固定 shape 离线场景，控制流和动态 shape 是短板
- **ATB Graph**：MindIE 原生图语言，开发成本高但优化最深，多卡大模型吞吐最优

## 十四、推理框架设计原理与模型架构演进

> 本章以算法工程师视角审视推理框架的核心设计思想和模型架构的演进逻辑——理解"为什么这样设计"，才能在适配时做出正确的工程判断，而不只是照着 API 文档照猫画虎。

---

### 14.1 推理框架的核心设计问题

LLM 推理框架的所有核心设计，都在解答同一个问题：**如何在内存受限的硬件上，高效服务动态长度、动态批次的生成请求。**

#### 14.1.1 为什么需要 Continuous Batching（连续批处理）

**传统静态批处理的问题**：一批请求同时开始、同时结束。生成 token 数差异极大（从 10 到 2000），先完成的请求只能等最长的那个——整批 GPU 利用率被最慢的请求拖垮。

**Continuous Batching 的设计思路**：调度器以 **iteration 为粒度**，每生成一步就检查哪些请求已完成，立刻将新请求填入空出的 slot。从宏观看，GPU 始终在处理一个满批次的"动态组合"，吞吐接近静态批处理的理论上限。

这一设计改变了适配工作的一个重要约束：**框架不再要求所有请求有相同长度**——模型 forward 必须能处理可变长度的 token 序列（packed input），这也是 vLLM 的 `input_ids` 是一维拼接而非二维 padding 张量的根本原因。

#### 14.1.2 PagedAttention 的设计动机

**问题根源**：KV cache 必须在请求开始时预分配（因为不知道输出多长），而每个请求的实际使用量远小于预分配量。大量内存因"预分配碎片"和"已完成请求的残留"被浪费。

**核心洞察**：借鉴操作系统的虚拟内存分页思想——KV cache 不再对应连续物理内存，而是被切分成固定大小的 **Block**（通常 16 个 token 一块），物理 Block 按需分配，逻辑地址通过 Block Table 映射到物理地址。

**带来的适配约束**：attention kernel 不能假设 KV 在内存中连续，必须通过 `block_tables` 索引跳跃式访问——这就是为什么适配新模型时必须用 `Attention(PagedAttention)` 而不能直接用 PyTorch 原生 attention。PagedAttention 把内存管理的复杂度从模型层移到了框架层。

**Prefix Caching 的自然延伸**：相同前缀的请求（系统提示、RAG 检索内容）可以共享 Block——同一个物理 Block 被多个请求的逻辑地址映射，无需重复计算。这是 Prefix Cache 命中率高的根本机制，并非只是简单的缓存 lookup。

#### 14.1.3 Prefill-Decode 分离的技术动因

混合批次中，Prefill token（一批几百个）和 Decode token（每请求 1 个）同时存在，导致两个深层矛盾：

**矛盾一：注意力计算的形状冲突**

Prefill 的 attention 是 `[seq_len, seq_len]` 的矩阵乘（可以用 FlashAttention），Decode 的 attention 是 `[1, seq_len]` 的向量-矩阵乘（不能用 FlashAttention，用专门的 PagedAttention decode kernel）。两种 attention 无法在同一个 kernel 里高效处理，强行混合必须有一边妥协。

**矛盾二：批次大小对两阶段的影响相反**

- Prefill 阶段：大 batch → FlashAttention 的 tile 复用效率高 → 吞吐提升
- Decode 阶段：大 batch → 每次权重读取被更多 token 摊销 → 带宽效率提升

两个阶段都需要"大 batch"，但 batch 的含义不同：Prefill 的 batch 是输入序列数，Decode 的 batch 是并发请求数。分离后，各自独立地最大化自己的批次效率。

**工程师应当理解的本质**：PD 分离不是简单的"两个服务"，而是把 KV cache 的产生（Prefill）和消费（Decode）解耦，允许两类计算各自用最合适的硬件和批次策略。KV cache 的高效传输（Mooncake、RDMA）是 PD 分离的工程核心，不是模型适配的核心。

---

### 14.2 注意力机制的演进脉络

注意力机制是适配工作中变化最频繁的部分。理解每次演进的**动机**，才能在遇到新变体时快速判断适配难点。

#### 14.2.1 从 MHA 到 GQA/MQA：推理效率的第一次革命

**MHA 的瓶颈**：标准多头注意力中，Q/K/V 各有 `num_heads` 个头。Decode 时 KV cache 大小 ∝ `num_heads × head_dim × seq_len`，70B 模型在 4096 序列长度下 KV cache 已达 ~35GB，KV cache 成为显存的主要消耗。

**GQA（Grouped Query Attention）的设计选择**：多个 Q head 共享一组 K/V head，KV cache 缩减比例 = `num_attention_heads / num_key_value_heads`（通常 4:1 或 8:1）。Llama3/Qwen2/Gemma3 全部采用 GQA。精度损失几乎可忽略（GQA 论文：在相同参数量下，GQA 比 MQA 精度高，比 MHA 接近）。

**适配影响最大的地方**：KV cache 的 `shape[2]`（head 数维度）必须用 `num_key_value_heads` 而非 `num_attention_heads`——这是 GQA 模型最常见的适配错误。

#### 14.2.2 MLA（Multi-head Latent Attention）：KV 压缩的第二次革命

GQA 是通过"减少 KV head 数"来降低 KV cache，MLA 的思路更激进：**用低秩矩阵压缩 KV 本身**。

**核心设计**：不存储 K/V，而是存储一个低秩的"潜变量" `c_KV`（维度 `kv_lora_rank`，通常 512，远小于 `num_heads × head_dim`），K/V 在 attention 时从 `c_KV` 即时展开。

```
标准 GQA（8 kv heads, head_dim=128）：每 token KV cache = 8 × 128 × 2 = 2048 bytes
MLA（kv_lora_rank=512）：           每 token KV cache ≈ 512 × 2 = 1024 bytes（节省约 50%）

DeepSeek-V3 实际：kv_lora_rank=512, num_heads=128, head_dim=128
传统 GQA 等效：   每 token 约 64 KB（128 heads × 128 dim × 2 bytes × 2 K/V）
MLA 实际：       每 token 约 1 KB，压缩比约 64×
```

**推理时的矩阵吸收优化**：由于 K/V 是线性展开，推理时可以把 `W_UK` 吸收进 `W_Q`，把 `W_UV` 吸收进 `W_O`，避免每次 forward 都做 low-rank expand，等效于减少了计算量。这是 MLA 在 vLLM 中需要专门实现 `absorb_kv_a_proj_with_mqa` 的原因。

**适配难点**：MLA 不能套用 GQA 的 PagedAttention kernel。标准 paged attention 假设 KV 已在 cache 中展开，但 MLA 存的是压缩后的 `c_KV`，需要专门的 MLA-aware attention kernel（vLLM 已实现，但在适配新变体时需确认 kernel 支持）。

#### 14.2.3 滑动窗口注意力（SWA）：长上下文的稀疏化路径

**动机**：标准 attention 的计算和内存复杂度都是 O(seq_len²)，128k 上下文的 attention map 已达 16GB。滑动窗口将每个 token 的 attention 范围限制在最近 W 个 token，复杂度降为 O(seq_len × W)。

**局部+全局交替的设计哲学**：仅有局部 attention 会导致模型无法捕捉长距离依赖（如文章开头和结尾的关系）。Mistral/Gemma3 的解法是大多数层用局部 attention，每隔 N 层插入一个全局 full attention 层——局部层做细粒度特征提取，全局层做跨段信息汇聚。

**适配的关键决策**：判断每一层用哪种 attention 的逻辑必须在模型代码层确定，KV cache 分配也因此不同（滑动窗口层只需 `min(seq_len, window_size)` 的 KV，可以节省大量内存）。PP 并行时每个 stage 都需要知道本 stage 各层的类型。

---

### 14.3 量化的数学本质与误差来源

理解量化误差从哪里来，才能判断什么情况下量化安全，什么情况下必须跳过某层。

#### 14.3.1 量化误差的两个来源

**误差来源一：表示范围截断（clipping）**

浮点数的数值范围远大于整数。量化时需要确定一个缩放因子（scale）将浮点值映射到 [-127, 127]（INT8）。如果某些值超出范围，会被截断为最大/最小值——这部分误差是不可逆的。

**LLM 的 outlier 问题**：LLM 的激活值中存在少量极大的"异常值"（outlier），往往比大多数值大 10-100×。INT8 的 scale 一旦为了覆盖这些 outlier 而设得很大，普通值的精度就会极低（大量值量化为 0）。这是为什么早期 INT8 量化 LLM 精度很差，而 SmoothQuant / AWQ 通过"预处理转移 outlier" 后才能实用。

**误差来源二：舍入误差（rounding）**

浮点值在量化区间内的位置不是整数，舍入产生误差。这部分误差是随机的，通常可通过校准（calibration）最小化。

#### 14.3.2 为什么有些层不能量化

| 层类型 | 不能量化的原因 |
|--------|-------------|
| **Embedding 层** | 词表中每个 token 对应一行权重，量化精度低会导致 token 表示混淆，影响所有 token |
| **LM Head** | 输出 logits 的精度直接决定 top-k 采样的概率分布，量化导致低概率 token 被错误拉高 |
| **RMSNorm** | 参数极少（hidden_size 个），量化无显存收益，但精度损失与层数线性叠加 |
| **MoE Router** | 路由错误的影响是非线性的——路由到错误专家，该 token 的整个 FFN 计算都是噪声 |
| **首尾几层** | 输入层（raw token embedding → 第一个 Transformer 层）和最后几层对精度最敏感，是误差积累的起点和终点 |

#### 14.3.3 量化粒度的权衡

| 粒度 | 精度 | 速度 | 内存开销 |
|------|------|------|---------|
| **Per-tensor** | 最低（单一 scale 覆盖整层） | 最快（scale 是标量） | 最小 |
| **Per-channel** | 中（每个输出 channel 一个 scale） | 稍慢 | 小（scale 向量） |
| **Per-group（如 g128）** | 较高（每 128 个权重一个 scale） | 中 | 中（scale 矩阵） |
| **Per-token 激活** | 高（激活量化，动态 scale） | 最慢（推理时计算 scale） | 无额外存储 |

AWQ 的 per-group INT4（group=128）之所以精度接近 FP16，是因为 group-wise scale 有足够粒度捕捉局部 outlier，而不是用一个全局 scale 覆盖所有值。

---

### 14.4 模型架构与推理效率的 Co-design 趋势

主流大模型架构的演进越来越以"推理效率"为核心设计目标，而不只是拟合训练指标。理解这个趋势有助于判断未来新模型的适配方向。

#### 14.4.1 KV Cache 是架构设计的中心约束

当模型服务大量用户时，KV cache 占据了大部分显存，比模型权重本身还大。这直接影响到可服务的并发用户数（KV cache 越大 → 并发越低）。

架构师在设计新模型时现在会明确考量：

- **GQA ratio**（num_heads / num_kv_heads）：越大 KV cache 越小，但过大影响模型表达能力
- **kv_lora_rank**（MLA 中）：越小 KV cache 越小，但展开误差越大
- **head_dim**：越小 KV cache 越小，但 attention 的表达能力也下降

这也是为什么 DeepSeek V3 的 MLA 和 Qwen3-MoE 的 GQA 都把 KV 压缩做到极致——在同等显存下服务更多并发用户，直接影响服务成本。

#### 14.4.2 MTP（Multi-Token Prediction）：训推一体的加速设计

**设计动机**：投机解码（speculative decoding）可以 2-3× 加速，但需要独立的 draft 模型。MTP 把 draft 能力直接内置于主模型：训练时让模型预测接下来 N 个 token（不只是 1 个），推理时可以利用这些额外的"猜测"做并行验证。

**工程含义**：适配 DeepSeek V3 这类内置 MTP 的模型时，权重中会有额外的 `model.layers.{N}.output_head_N` 参数，load_weights 必须处理这些多余权重（跳过或加载），并且 forward 的输出格式也不同（返回多个 token 的 logits，而非单个）。

**推断能力越来越成为训练目标的一部分**：MTP 是"训练时同时优化推理速度"的早期范例。预计未来会有更多"训推协同设计"的架构特性，适配工程师需要理解这类新特性的原理而不只是接口。

#### 14.4.3 SSM/Mamba 与混合架构的设计权衡

State Space Model（SSM，以 Mamba 为代表）提供了与 Transformer attention 完全不同的序列建模机制：

| 维度 | Transformer Attention | Mamba / SSM |
|------|----------------------|-------------|
| **长序列复杂度** | O(n²) 时间，O(n) KV 存储 | O(n) 时间，O(1) 状态存储 |
| **上下文访问** | 全部历史（random access） | 压缩进固定大小的隐状态（有损） |
| **推理 KV cache** | 随 seq_len 线性增长 | 固定大小（不随 seq_len 增长） |
| **适配难点** | 标准，工具链成熟 | 状态更新需专用 scan kernel，KV cache 语义不同 |

**混合架构的兴起**（Jamba、Zamba、Falcon Mamba）：在同一模型中交替使用 Attention 层和 SSM 层，兼顾 Attention 的精确长距离建模和 SSM 的高效状态压缩。适配这类模型需要同时实现两套机制，且 KV cache 管理也需要区分 attention 层（传统 KV）和 SSM 层（固定大小隐状态）。

**当前判断**：SSM 和混合架构在超长上下文（>512k token）的在线推理场景有优势，但对话、代码、推理等主流任务上 Transformer 仍是最优选。短期内 Transformer 不会被取代，混合架构是渐进式融合。

### 14.5 推理内核（Kernel）的设计演进

理解 kernel 的设计，是理解"为什么某些操作快、某些操作慢"的基础，也是评估新硬件适配难度的关键。

#### 14.5.1 FlashAttention 的设计原理

**问题**：标准 attention 需要存储完整的 `[seq_len, seq_len]` attention map，对 4096 长度来说是 64M 个浮点数（256MB），反复在 HBM 和 SRAM（片上高速缓存）之间搬运，内存访问次数极多。

**核心思想**：将 Q/K/V 分成小块（tile），在 SRAM 内完成一个 tile 的 attention 计算，只需把结果写回 HBM，避免写入/读取完整的 attention map。通过 online softmax 算法保证数值等价。

**关键约束**：FlashAttention 要求 Q/K/V 在 attention 维度连续存储（`BSND` 或 `BNSD` layout），并且 `head_dim` 必须满足 tile 对齐（通常 64/128/256 的倍数）。这是昇腾 FlashAttentionScore 要求 `head_dim` 为 16/32 倍数的底层原因。

**FA2 vs FA3**：FA3 专门为 Hopper（H100）的 Warp Specialization 和异步内存流水线优化，在 H100 上比 FA2 快 1.5-2×，但无法移植到非 Hopper 硬件。适配时需注意后端选择逻辑（vLLM 根据 GPU 架构自动选择）。

#### 14.5.2 算子融合的价值与局限

算子融合（operator fusion）是将多个连续的小算子合并为一个 kernel，消除中间 tensor 的 HBM 读写。典型案例：

- `LayerNorm + Linear`：LayerNorm 的输出是 memory bound（写 HBM），Linear 的输入读 HBM；融合后 LayerNorm 结果保留在 SRAM 直接进入 Linear，节省一次 HBM 往返
- `Bias + ReLU + Dropout`：三个逐元素操作合并为一次 kernel，内存访问减少 2/3

**局限**：融合 kernel 的实现依赖具体硬件架构，跨硬件移植时融合 kernel 需要重写。这是 GPU 融合 kernel 不能直接移植到昇腾的根本原因，也是 MindIE Turbo 需要单独开发 ATB 融合 kernel 的原因。

**vllm-ascend 的 Npugraph_ex** 做的正是自动化的算子融合：通过 PyTorch FX 图分析，自动检测可融合的算子序列，生成融合 kernel，无需手写每种融合组合——这是其相对于手写融合 kernel 的核心工程价值。

#### 14.5.3 从 kernel 视角理解量化加速

量化加速不只是"数据小所以快"，而是有具体的硬件机制支撑：

- **INT8 GEMM**：H100 的 Tensor Core 对 INT8 矩阵乘的吞吐是 FP16 的 2×（FP16: 1979 TFLOPS, INT8: 3958 TOPS），带宽需求也减半（INT8 weight 比 FP16 小一半）
- **FP8 E4M3**：H100 FP8 的 Tensor Core 吞吐是 FP16 的 2×（3979 TFLOPS），精度高于 INT8（有指数位），是 H100 量化的最优选
- **GPTQ / AWQ 的 INT4 kernel**：INT4 没有原生硬件支持（Tensor Core 最低支持 INT8），必须先 unpack INT4 到 INT8/FP16 再做 GEMM。Marlin kernel 的优化在于把 unpack 和 GEMM 流水线化，避免 unpack 成为瓶颈

**昇腾的量化硬件支持**：910B 的 Cube 单元（类 Tensor Core）支持 INT8 矩阵乘，W8A8 量化能直接走 Cube 单元，性能收益显著；FP8 支持在 910C 后逐步引入。

### 14.6 框架设计的长期演进方向

理解框架的演进方向，有助于判断当前的适配投资是否会被下一代框架设计抹掉。

#### 14.6.1 vLLM V1 重构的设计目标

vLLM 的 V1 架构重构（2025 年进行中）解决了 V0 设计的几个根本问题：

**问题一：Worker 模型耦合**。V0 中每个 Worker 进程独立运行，调度信息通过 IPC 传递，通信开销大。V1 引入统一的 Worker 模型，调度在主进程完成，Worker 只做计算。

**问题二：CUDAGraph 覆盖不完整**。V0 的 CUDAGraph 只覆盖 decode 路径，prefill 每次走 eager。V1 通过统一的 `forward_metadata` 抽象，让 prefill 和 decode 都能在一套 CUDAGraph 下执行。

**问题三：PD 分离难以原生支持**。V0 的设计假设 prefill 和 decode 在同一个 Worker 中，PD 分离需要大量 hack。V1 把 prefill 和 decode 解耦为独立的 execution loop，PD 分离成为一等公民。

**对适配工程师的影响**：V1 后，模型的 `forward` 方法签名会有变化（`attn_metadata` 结构调整），旧模型需要更新对 `forward` 的调用方式——但好消息是 V1 的 API 比 V0 更清晰，适配成本应当更低。

#### 14.6.2 编译器驱动的推理优化

torch.compile 和 XLA/Dynamo 的成熟，正在让"手写 CUDA kernel"变得不那么必要——编译器能自动生成高质量的融合 kernel。这改变了推理框架的优化工作重心：

**过去（pre-compile 时代）**：瓶颈操作手写 CUDA kernel → 高度优化但硬件绑定

**现在（compile 时代）**：用高级语言（Triton、Liger Kernel）描述算子逻辑 → 编译器负责 tile 策略、内存布局、融合机会

**昇腾的追赶路径**：torchair（torch.compile → Ascend GE）和 Npugraph_ex（PyTorch FX 图优化）都是走编译器路线，而非重写 CUDA kernel。长期来看，这条路线的维护成本远低于手写 kernel，是昇腾生态追赶 NVIDIA 的关键手段。

#### 14.6.3 推理即服务（Inference-as-a-Service）的框架抽象趋势

推理框架正在从"运行模型的工具"演变为"提供推理能力的平台"，核心体现在：

- **模型无关的优化**（PD 分离、EPLB、投机解码）不再需要模型感知，框架层统一实现
- **硬件抽象层**（vLLM 的 Platform 插件、MindIE Motor）让同一个模型代码跑在不同硬件上
- **服务质量（QoS）感知的调度**：不同优先级请求的资源隔离，正在从外部负载均衡迁移进框架内部

对适配工程师而言，这意味着适配工作的核心将持续缩小——未来大多数"适配工作"将是：确认模型架构在框架的支持矩阵内，写正确的 `load_weights` 和 `forward`，框架负责所有调度、并行、量化、加速的细节。

这不是说适配工作会消失，而是**适配工作的重心会从"让模型跑起来"转移到"让模型在新硬件/新场景下高效跑起来"**——更多的架构理解，更少的 boilerplate 代码。

## 十五、Coredump / Segfault 定位方法论

> 在 vllm-ascend 上开发 MTP、投机解码、图模式等底层特性时，C++/NPU kernel 层面的崩溃是家常便饭。Python traceback 消失、进程直接 killed、多进程只有一个 rank 挂掉——这类问题不能靠 print 调试，需要一套系统性的定位方法论。

---

### 15.1 崩溃类型速判

遇到崩溃，第一步是识别崩溃类型，不同类型的根因和定位路径完全不同：

| 崩溃现象 | 类型 | 根因层次 | 定位入口 |
|---------|------|---------|---------|
| Python `Exception` + 完整 traceback | Python 异常 | Python 层 | 直接看 traceback |
| `Segmentation fault (core dumped)` | C 层内存违规 | C++/CANN 扩展 | gdb 分析 core |
| `Aborted (core dumped)` | `assert` 或 `SIGABRT` | C++ 断言 / CANN 内部 | gdb + CANN 日志 |
| `Killed` | OOM Killer | 内存超限 | `dmesg` 查 OOM 日志 |
| 进程静默消失，无任何输出 | `SIGKILL` 或 `exit(-1)` | 多进程协调失败 | 进程退出码 + rank 日志 |
| NPU 进程挂起不退出 | 死锁 / HCCL hang | NPU 集合通信卡住 | 超时 + `pstack` |
| `RuntimeError: CANN error: ...` | CANN API 错误 | CANN/ATB 算子 | CANN 错误码 + ATB 日志 |

**关键判断：是 Python 崩溃还是 C 崩溃？**

```bash
# Python 异常不会产生 core 文件；C 崩溃会（如果 ulimit 允许）
# 先检查是否有 core 文件
ls -la core* /tmp/core* 2>/dev/null

# 查看进程退出码（非零表示异常退出）
echo $?
# 139 = SIGSEGV; 134 = SIGABRT; 137 = SIGKILL(OOM)
```

---

### 15.2 环境准备：让崩溃信息尽可能完整

崩溃发生后才想起没配环境是最大的浪费。**在开发阶段就配好以下设置**：

#### 开启 core dump

```bash
# 允许生成完整 core 文件（不限制大小）
ulimit -c unlimited

# 设置 core 文件路径（避免写到工作目录找不到）
echo '/tmp/core.%e.%p.%t' | sudo tee /proc/sys/kernel/core_pattern
# %e=程序名, %p=pid, %t=时间戳

# 验证：运行一个必然崩溃的程序
python3 -c "import ctypes; ctypes.string_at(0)"
ls /tmp/core.*   # 应当出现 core 文件
```

#### 保留调试符号

vllm-ascend 和 torch_npu 的 Release 包通常剥离了调试符号，gdb backtrace 只有地址没有函数名。解决方案：

- **优先**：从源码构建 Debug 版本（`CMAKE_BUILD_TYPE=Debug`）
- **退而求其次**：安装对应的 debuginfo 包（部分发行版提供 `torch-debuginfo`）
- **最低保障**：用 `addr2line` + `.so` 文件做地址到行号的离线映射

#### CANN/ATB 调试日志提前开启

```bash
# CANN 错误详细输出
export ASCEND_GLOBAL_LOG_LEVEL=0       # 0=DEBUG, 1=INFO, 2=WARNING, 3=ERROR
export ASCEND_SLOG_PRINT_TO_STDOUT=1   # 同时输出到 stdout（不只写文件）
export ASCEND_LAUNCH_BLOCKING=1        # NPU 算子同步执行（异步 bug 同步复现）

# ATB 崩溃保护
export ATB_LOG_LEVEL=DEBUG
export ATB_DUMP_ENABLE=1               # 崩溃前 dump 最后一次 tensor 输入
export ATB_DUMP_PATH=/tmp/atb_crash_dump

# Python 层：遇到 warning 直接报错，不要吞掉
export PYTHONWARNINGS=error
```

**`ASCEND_LAUNCH_BLOCKING=1` 是最重要的设置**：默认 NPU 算子异步提交，崩溃时 Python 调用栈已经走到很后面，crash 位置和根因相差甚远。同步模式下崩溃点就是根因所在。

### 15.3 Python 层定位

在 C 崩溃之前，通常有 Python 层的信号可以提前捕捉。

#### 捕捉 C 扩展崩溃前的 Python 栈

Python 进程被 SIGSEGV 杀死时，Python 自身的 signal handler 来不及打印 traceback。用 `faulthandler` 模块可以在 crash 发生时同步输出当前 Python 栈：

```python
# 在入口最前面加上（不影响性能，建议常态化）
import faulthandler
faulthandler.enable()          # 崩溃时自动打印 Python 栈到 stderr
# 或者输出到文件，避免多进程日志混乱
faulthandler.enable(open('/tmp/fault.log', 'w'))
```

崩溃时 stderr 会出现类似：
```
Fatal Python error: Segmentation fault

Current thread 0x00007f... (most recent call first):
  File "vllm/worker/model_runner.py", line 312 in execute_model
  File "vllm/worker/worker.py", line 241 in _execute_model_spmd
  ...
```

这能精确告诉你崩溃发生在哪个 Python 调用链上，是定位 C 扩展崩溃的第一步。

#### 多进程环境下的日志隔离

vLLM 使用多进程（每个 TP rank 一个进程），崩溃往往只在某个 rank 发生，而其他 rank 因为 `dist.barrier()` 挂起。必须为每个 rank 配置独立日志：

```bash
# 启动时设置 rank-specific 日志
VLLM_LOGGING_LEVEL=DEBUG \
VLLM_LOG_FILE=/tmp/vllm_rank_{rank_id}.log \  # 框架支持则用这个
python -m vllm.entrypoints.openai.api_server ...

# 如果框架不支持，在代码里手动区分
import os, logging
rank = int(os.environ.get('RANK', 0))
logging.basicConfig(filename=f'/tmp/rank_{rank}.log', level=logging.DEBUG)
```

崩溃后检查所有 rank 的日志，找到最后一条日志之后就是 crash 点。

### 15.4 C++ 层：gdb 分析 Core Dump

gdb 分析 core dump 是定位 segfault/abort 的核心手段。

#### 基本 core dump 分析流程

```bash
# 1. 加载 core 文件（python3 是解释器，core 是 dump 文件）
gdb python3 /tmp/core.python3.12345.1720000000

# 2. 查看崩溃时的 C++ 调用栈
(gdb) bt           # backtrace，显示完整调用链
(gdb) bt full      # 同时显示各帧的局部变量

# 3. 切换到特定帧，检查变量
(gdb) frame 3      # 切换到第 3 帧
(gdb) info locals  # 查看当前帧局部变量
(gdb) print var    # 打印特定变量

# 4. 查看寄存器（崩溃现场）
(gdb) info registers

# 5. 查看崩溃地址附近的内存
(gdb) x/20x $rsp   # 查看栈顶附近 20 个十六进制字
```

#### 在 gdb 中查看 Python 调用栈

如果安装了 Python 的 gdb 扩展（`python3-dbg` 或 `libpython3.x-dbg`）：

```bash
(gdb) py-bt        # 打印 Python 级别的调用栈（与 C 栈对应）
(gdb) py-list      # 显示当前 Python 帧的源码
(gdb) py-locals    # 当前 Python 帧的局部变量（对象级别）
```

这让你同时看到：`C++ frame 5: ATB_FlashAttentionOp::execute()` 对应的是 `Python frame: vllm_ascend/ops/attention.py:line 127`。

#### 没有调试符号时用 addr2line

```bash
# 从 bt 中找到崩溃地址和 .so 文件
# 例如：#3  0x00007f1234567890 in ?? () from /usr/lib/libatb.so

# 获取 .so 加载基地址
(gdb) info sharedlibrary libatb
# 输出：0x00007f1234000000  /usr/lib/libatb.so

# 计算偏移量 = 崩溃地址 - 基地址
python3 -c "print(hex(0x00007f1234567890 - 0x00007f1234000000))"
# 输出：0x567890

# 用 addr2line 查行号（需要未剥离符号的 .so，或源码编译版本）
addr2line -e /usr/lib/libatb.so -f 0x567890
```

### 15.5 NPU 层：CANN/ATB 崩溃定位

vllm-ascend 特有的崩溃往往在 CANN/ATB 层，标准 gdb 只能看到 C++ 调用到了某个 NPU API，但不知道 NPU 内部发生了什么。

#### CANN 错误日志位置

CANN 将详细错误写入日志文件，默认路径：

```bash
# CANN 运行日志
~/.davinci/log/
/var/log/npu/slog/

# 关键文件
plog-*.log   # 进程级日志，按 pid 命名
device-*.log # 设备日志，含 kernel 执行错误

# 实时查看（崩溃发生时）
tail -f ~/.davinci/log/plog-$(pgrep python).log
```

CANN 错误通常有错误码，如 `EZ9999`、`ACL_ERROR_INVALID_PARAM`，可直接查昇腾官方错误码文档定位含义。

#### ACL/ATB 算子崩溃的典型模式

**模式一：Shape 不匹配导致 kernel 越界**

ATB 算子在 C++ 层做 shape 校验，不通过时调用 `abort()`。gdb 的 backtrace 会出现 `atb::BaseOperation::Execute → shape_check_fail`。解法：在 Python 层把所有输入 tensor 的 shape 打印出来，对照算子的 API 文档检查约束。

**模式二：未初始化的 tensor 传入 NPU 算子**

Python 端创建了一个 tensor 但没有正确赋值（如 `torch.empty` 后直接传入，或 buffer 分配出错），NPU 读到非法内存地址。特征：crash 地址在某个 NPU 内存区域，CANN 日志有 `device memory access fault`。

**模式三：NPU 和 CPU tensor 混用**

将 CPU tensor 传入 NPU 算子（或反之），CANN 在 C++ 层检查到 device 不匹配时 abort。特征：backtrace 有 `check_device_type` 调用。解法：在算子调用前加 `assert tensor.device.type == 'npu'`。

**模式四：多卡 HCCL 通信超时后的 SIGABRT**

一个 rank 崩溃后，其他 rank 在 `dist.all_reduce()` 等待超时，最终被 HCCL 以 SIGABRT 杀死。特征：所有 rank 的 crash 时间几乎一致，backtrace 都在 HCCL 函数内。

定位方法：
1. 找**最先崩溃**的 rank（时间戳最早）
2. 在该 rank 的日志中找崩溃前最后一条 NPU 操作日志
3. 该操作就是根因，其他 rank 是受害者

```bash
# 找最先崩溃的 rank
for i in 0 1 2 3 4 5 6 7; do
    echo "rank $i last log:"
    tail -1 /tmp/rank_${i}.log
done
```

#### ACLGraph 捕获阶段崩溃

MTP、投机解码等特性开发时，如果 ACLGraph 捕获（warmup）阶段 crash，原因通常是：

- **动态控制流进入图**：graph capture 期间遇到 `if/else` 或 Python 函数调用，导致 capture 逻辑混乱
- **跨 stream 的 tensor 依赖**：MTP 的多步 forward 可能产生跨 stream 的数据依赖，capture 时未正确处理同步点
- **shape 在 capture 和 replay 间变化**：warmup 时用固定 shape，replay 时 shape 不匹配

临时关闭图模式来隔离问题：

```bash
export VLLM_ASCEND_CUDAGRAPH_MODE=NONE   # 强制 eager，确认 eager 正确后再开图模式
```

### 15.6 内存错误：AddressSanitizer（ASAN）

对于**堆内存越界、use-after-free、double-free** 等难以复现的内存错误，gdb 只能看到结果（crash），ASAN 能精确定位分配/释放的原始位置。

#### 启用 ASAN

```bash
# 方法一：编译 torch_npu / vllm-ascend 时开启 ASAN
# 在 CMakeLists.txt 或 setup.py 添加：
# -fsanitize=address -fno-omit-frame-pointer

# 方法二：运行时注入（适合不重新编译的情况，但覆盖不完整）
LD_PRELOAD=/usr/lib/x86_64-linux-gnu/libasan.so.5 python3 your_script.py

# ASAN 环境变量：定制输出
export ASAN_OPTIONS="detect_leaks=0:halt_on_error=0:log_path=/tmp/asan.log"
# detect_leaks=0：关闭内存泄漏检测（推理中大量正常的长生命周期内存）
# halt_on_error=0：不在第一个错误停止，收集所有错误
```

ASAN 输出示例：
```
==12345==ERROR: AddressSanitizer: heap-buffer-overflow on address 0x...
READ of size 4 at 0x... thread T0
    #0 0x... in ATBAttentionOp::execute /path/to/atb_attention.cpp:234
    #1 0x... in ...

0x... is located 8 bytes after a 256-byte region [0x..., 0x...)
allocated by thread T0 here:
    #0 0x... in malloc
    #1 0x... in ATBAttentionOp::init /path/to/atb_attention.cpp:112
```

这精确告诉你：在 `atb_attention.cpp:234` 读越界，内存在 `line:112` 分配。

#### ASAN 与 NPU 的兼容性说明

CANN 本身不支持 ASAN 全面覆盖（NPU 内核在设备端执行，ASAN 只覆盖 CPU 侧内存）。因此：
- ASAN 能发现**CPU 侧的 C++ 内存错误**（ATB Python 绑定层、vllm C 扩展）
- ASAN **不能覆盖** NPU HBM 内存的越界（那是 CANN 的 device memory 检查范围）
- 若崩溃源于 NPU 内存，仍需依赖 CANN 日志和 ATB_DUMP

### 15.7 多进程与分布式场景的定位技巧

vLLM 在 TP > 1 时以多进程运行，常规调试方式需要适配。

#### 挂载 gdb 到运行中的进程

```bash
# 找到目标 rank 的 pid
ps aux | grep python | grep rank_0   # 或通过环境变量 RANK=0 过滤

# 挂载 gdb（不需要 core 文件，直接 attach 运行中的进程）
gdb -p <pid>

# attach 后进程暂停，查看当前调用栈
(gdb) bt
(gdb) continue   # 继续运行
```

对于 HCCL hang（所有进程卡在通信等待），用 `gdb -p <pid>` attach 后立刻 `bt`，可以看到卡在哪个通信原语上。

#### 为每个 rank 设置独立的崩溃处理

vLLM 多进程环境下，可以在 Worker 初始化时为每个 rank 注册 signal handler：

```python
import signal, sys, traceback, os

def crash_handler(signum, frame):
    rank = int(os.environ.get('RANK', 0))
    with open(f'/tmp/crash_rank_{rank}.log', 'w') as f:
        f.write(f"Rank {rank} received signal {signum}\n")
        traceback.print_stack(frame, file=f)
    sys.exit(1)

signal.signal(signal.SIGSEGV, crash_handler)   # 捕捉 segfault
signal.signal(signal.SIGABRT, crash_handler)   # 捕捉 abort
```

**注意**：SIGSEGV 的 signal handler 本身可能在 corrupt 的 stack 上运行导致再次崩溃，因此 handler 要尽量简单（只写文件，不做复杂操作），并且与 `faulthandler.enable()` 配合使用（faulthandler 更可靠）。

#### Ray 环境下的崩溃

vLLM 可选用 Ray 作为多进程后端，Ray Actor 崩溃时会被 Ray 自动重启，崩溃日志写入 Ray 的日志目录：

```bash
# Ray 日志位置
~/.local/share/ray/session_*/logs/

# 查看特定 Actor 的日志（按 pid 找）
ls ~/.local/share/ray/session_latest/logs/worker-*.err
```

Ray Actor 的崩溃日志往往比 vLLM 自身的日志更完整（包含 C++ 崩溃信息），优先查这里。

### 15.8 MTP 开发的典型 Crash 场景

MTP（Multi-Token Prediction）开发涉及多步 forward 和 draft token 验证，有几类特有的 crash：

#### Crash 场景一：draft token 的 attention state 污染

MTP 的验证步骤需要用主模型的 KV cache 做多步 attention。如果 draft 阶段错误地把中间状态写入主模型的 KV cache slot，下次 decode 时会读到污染数据，轻则精度异常，重则访问越界崩溃。

定位方法：用 `ATB_DUMP_ENABLE=1` 在 MTP 验证步前后分别 dump KV cache，对比 slot 内容是否被意外修改。

#### Crash 场景二：多步 forward 中 position_ids 溢出 rope 缓存

MTP 的 draft 步骤会产生超出当前 seq_len 的 position_ids（预测第 t+1, t+2, ... 个 token 的位置），如果 RoPE 的 cos/sin 缓存预计算长度不够，索引会越界，在 C 层触发 segfault。

定位方法：在 RoPE forward 前 assert：`assert positions.max() < self.max_seq_len_cached`，把 C 崩溃提前变成 Python 异常。

#### Crash 场景三：ACLGraph 捕获 MTP forward 时的形状问题

MTP 的 forward 与 standard decode forward 的 token 数不同（draft step 可能一次处理多个 draft token），但 ACLGraph 的 FULL 模式按 token 数分 bucket。如果 MTP 的 draft token 数不在预定义的 bucket 里，graph replay 时 shape 不匹配，触发 CANN assertion。

定位方法：
1. 先用 `cudagraph_mode=NONE` 确认 eager 下 MTP 正确
2. 切换到 `PIECEWISE` 模式（attention 以 eager 执行），缩小图化范围
3. 最后再尝试 FULL 模式，确认 bucket 配置覆盖了 MTP 需要的 token 数

#### Crash 场景四：投机解码验证阶段的 batch 维度错误

投机解码的验证步（verify step）需要同时处理 draft tokens 和验证结果，batch 维度从 `[num_seqs]` 变成 `[num_seqs × speculation_len]`。如果模型的某个算子（如 position_ids 生成、attention mask 构造）没有正确处理这个扩展后的 batch，会产生 shape 不匹配，在 C++ 矩阵乘法层崩溃。

定位方法：在 verify step 入口打印所有关键 tensor 的 shape，与标准 decode step 对比，找到第一个形状异常的 tensor。

### 15.9 系统性定位思路：从现象到根因的决策树

```
崩溃发生
    │
    ├─ 有 Python traceback？
    │       ├─ 有 → 直接看 traceback，定位到具体 Python 行
    │       └─ 无 → 检查 faulthandler 输出，获取 Python 栈
    │
    ├─ 有 core 文件？
    │       ├─ 有 → gdb 分析，重点看 bt 和 py-bt
    │       └─ 无 → ulimit -c unlimited 后重新复现
    │
    ├─ 能稳定复现？
    │       ├─ 是 → 二分法缩小范围（见下）
    │       └─ 否 → ASAN + ASCEND_LAUNCH_BLOCKING=1 + 多次运行
    │
    ├─ 多进程 vs 单进程？
    │       ├─ 先用 TP=1 PP=1 单进程复现
    │       └─ 单进程不崩溃 → 多进程通信或 shared memory 问题
    │
    └─ 崩溃层次？
            ├─ Python 异常 → 看 traceback
            ├─ C++ abort → gdb bt + CANN 日志
            ├─ NPU kernel → CANN 错误码 + ATB_DUMP
            └─ 内存错误 → ASAN + valgrind
```

**二分法缩小范围的三个维度**：

1. **层数二分**：怀疑某个 Transformer 层出问题，先跑只有 1 层的模型（`num_hidden_layers=1`），再 2 层、4 层……找到最小复现层数
2. **seq_len 二分**：MTP/投机解码的 crash 可能与序列长度相关，从 1 token 逐步增加
3. **特性二分**：关掉 MTP / 关掉 ACLGraph / 关掉量化，逐步开启，找到触发 crash 的最小特性组合

**最小复现的原则**：一旦找到"能稳定复现 crash 的最小用例"，调试效率会提升 10×。不要在全量配置下调试。

### 15.10 崩溃预防：防御性开发实践

在开发阶段嵌入检查，把 C 崩溃变成 Python 异常（更友好、更容易定位）：

**Tensor 健康检查**（在关键边界插入，不是每个算子都加）：

```python
def check_tensor(t, name, expected_device="npu"):
    assert not torch.isnan(t).any(), f"{name} contains NaN"
    assert not torch.isinf(t).any(), f"{name} contains Inf"
    assert t.device.type == expected_device, f"{name} on wrong device: {t.device}"
    assert t.is_contiguous(), f"{name} is not contiguous"
```

**Shape 预检查**（在调用 ATB/CANN 算子前）：

- 针对每个 ATB Operation，整理官方文档中的 shape 约束，封装成一个 `validate_inputs()` 函数，在 debug 模式下调用
- 开发完毕后可用 `if os.environ.get('DEBUG_CHECKS'): validate_inputs(...)` 保留但不常态执行

**MTP/投机解码的边界断言**：

- draft token 的 position_ids 必须单调递增且不超过 `max_seq_len`
- verify step 的 batch 维度必须等于 `num_seqs × speculation_len`
- KV cache 的 slot_mapping 在 draft 和 verify 步之间必须一致

这些断言在开发期应当常态打开，CI 中也要运行，只在性能 profiling 时关闭。
